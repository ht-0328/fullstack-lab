# 文書を書いて、評価して、直す

## 1. 書く

1. 種類と置き場所を [docs/README.md](../../../docs/README.md) の「種類と置き場所」で決めます。
2. ADR はテンプレート（[adr/TEMPLATE.md](../../../docs/adr/TEMPLATE.md)）を複製し、`> 書くこと:` と `> 例:` の行を自分の文に置き換えます。設計の文書（`docs/design/<フォルダ>/`）にはテンプレートが無いので、[docs/design/README.md](../../../docs/design/README.md) の「文書の単位と書き方」に沿い、同じフォルダの既存の文書を例にします。architecture、roadmap、索引は既存の構成のまま直します。
3. 「書き方（人が読める文書にする決まり）」W-1〜W-10 を守ります。特に、W-1 導入（表から始めない）、W-2 前提と用語（初出で一言）、W-3 表のリード、W-5 経緯と進み具合を書かない、の 4 つは機械的に確かめられます。

## 2. 評価する

1. 先に `python3 scripts/doc-lint.py <文書>` を実行し、出た指摘を直します。機械で決まる形式の指摘を、エージェントの評価に混ぜないためです。
2. `doc-review` エージェントに、対象の文書のパス、評価の形、`scripts/doc-lint.py` の出力を渡して評価させます。1 回目と決まりを変えたあとは全文評価です。2 回目以降は差分評価にし、`git diff <前回の評価のコミット> -- <文書>` の出力もプロンプトに貼ります。エージェントは文書を変えないようコマンドを実行するツールを持たないので、出力は呼び出し側が貼ります。エージェントの定義は [.claude/agents/doc-review.md](../../../.claude/agents/doc-review.md) です。エージェントとして起動できない環境では、その定義を読んで同じ手順で評価します。
3. 結果を [docs/review/](../../../docs/review/README.md) の記録に書きます。ファイル名と形は docs/review/README.md のとおりです。記録が無ければ作り、あれば「回ごとの結果」に 1 行足し、その回の要修正を「指摘の一覧」に 1 行ずつ（回、決まり、場所、直したか）足します。

## 3. 直す

1. 要修正をすべて直します。直し方の案をそのまま使ってよいですが、文脈に合わなければ書き直します。意味や決定の中身は変えません。
2. 直さないと決めた指摘は「残した指摘」に理由を書きます。理由が「決まりが曖昧」なら「決まり側の課題」にも書きます。
3. 文書 1 本の修正を 1 コミットにします。件名は `docs: <文書名> を doc-review の指摘で直す（N 回目）` です。

## 4. 止める

次のどちらかで止めます。

- 要修正が 0 件になった（合格）
- 前回と同じ指摘が残り、直しても減らない。その指摘は「残した指摘」に理由を書いて人に渡す

2 回目以降を差分評価にしているので、読む範囲は回ごとに縮み、評価は終わります。目安として、2026-11-02 に 14 本を評価したときは、2〜5 回目ですべて合格しました（[docs/review/README.md](../../../docs/review/README.md) の「合格までの回数の実績」）。1 回目か、決まりを変えたあとの全文評価から数えて 5 回を超えても合格しないときは、文書ではなく決まりかテンプレートに原因があるとみて、人に渡します。

合格したら、記録の先頭の表と「合格までの回数の実績」を更新します。

直さずに残した指摘と、決まりに反映しない「決まり側の課題」があれば、1 つにつき 1 つ集約リポジトリへ issue を起票し（[課題のテンプレート](../../../.github/ISSUE_TEMPLATE/issue.md)。同じ課題の issue があればコメントを足す）、記録からリンクします。

## 5. 決まりを育てる

複数の文書で同じ指摘が出たら、文書ではなく決まりかテンプレートを直します。docs/README.md の「書き方」の表に例を足す、設計の文書の決まりなら docs/design/README.md の「文書の単位と書き方」の表を直す、テンプレートの `> 書くこと:` を具体的にする、のどれかです。変えたら、変えた文書（docs/README.md か docs/design/README.md）の最終確認日を更新します。

決まりは、評価と修正を回している途中では変えません。途中で変えると、それまで合格していた文が新しい決まりで引っかかり、評価が終わらなくなるためです。「決まり側の課題」は記録にためておき、対象の文書がすべて合格したら、その場で決まりに反映するか、集約リポジトリに issue を起票します。記録にためたまま放っておきません。決まりを変えたら、影響する文書を全文評価し直します。決まりを書いた docs/README.md と、「文書の単位と書き方」の表を持つ docs/design/README.md 自身は、指摘を直すことがそのまま決まりを変えることになるので、差分評価で回し、合格したあとに 1 回だけ全文評価します。その全文評価で出た指摘は、直して差分評価で確かめ、合格したら終えます。判定の細かい扱いは、docs/README.md の「判定に迷うときの扱い」の表に 1 行足します（設計の文書の決まりなら、docs/design/README.md の「文書の単位と書き方」の表に足し、「判定に迷うときの扱い」からはリンクします）。

## 6. PR に書くこと

PR 本文の「テスト内容」に、文書ごとに「何回で合格したか」「残した指摘の件数」「決まり側の課題の件数と、反映したか起票したか（issue へのリンク）」を書き、記録ファイルにリンクします。評価の結果をユーザーに報告するときも、要修正だけでなく、決まり側の課題の件数を必ず伝えます。
