# 文書を書いて、評価して、直す

## 1. 書く

1. 種類と置き場所を [docs/README.md](../../../docs/README.md) の「種類と置き場所」で決めます。
2. 設計書と ADR はテンプレート（[design/TEMPLATE.md](../../../docs/design/TEMPLATE.md)、[adr/TEMPLATE.md](../../../docs/adr/TEMPLATE.md)）を複製し、`> 書くこと:` と `> 例:` の行を自分の文に置き換えます。architecture、roadmap、索引は既存の構成のまま直します。
3. 「書き方（人が読める文書にする決まり）」W-1〜W-10 を守ります。特に、W-1 導入（表から始めない）、W-2 前提と用語（初出で一言）、W-3 表のリード、W-5 経緯を書かない、の 4 つは機械的に確かめられます。

## 2. 評価する

1. 先に `python3 scripts/doc-lint.py <文書>` を実行し、出た指摘を直します。機械で決まる形式の指摘を、エージェントの評価に混ぜないためです。
2. `doc-review` エージェントに、対象の文書のパスと評価の形を渡して評価させます。1 回目と決まりを変えたあとは全文評価、2 回目以降は差分評価（前回の評価のコミットを渡す）にします。エージェントの定義は [.claude/agents/doc-review.md](../../../.claude/agents/doc-review.md) です。エージェントとして起動できない環境では、その定義を読んで同じ手順で評価します。
3. 結果を [docs/review/](../../../docs/review/README.md) の記録に書きます。ファイル名と形は docs/review/README.md のとおりです。記録が無ければ作り、あれば「回ごとの結果」に 1 行足し、その回の要修正を「指摘の一覧」に 1 行ずつ（回、決まり、場所、直したか）足します。

## 3. 直す

1. 要修正をすべて直します。直し方の案をそのまま使ってよいですが、文脈に合わなければ書き直します。意味や決定の中身は変えません。
2. 直さないと決めた指摘は「残した指摘」に理由を書きます。理由が「決まりが曖昧」なら「決まり側の課題」にも書きます。
3. 文書 1 本の修正を 1 コミットにします。件名は `docs: <文書名> を doc-review の指摘で直す（N 回目）` です。

## 4. 止める

次のどちらかで止めます。

- 要修正が 0 件になった（合格）
- 前回と同じ指摘が残り、直しても減らない。その指摘は「残した指摘」に理由を書いて人に渡す

2 回目以降を差分評価にしているので、読む範囲は回ごとに縮み、評価は終わります。目安として、2026-11-02 に 14 本を評価したときは、2〜5 回目ですべて合格しました（[docs/review/README.md](../../../docs/review/README.md) の「合格までの回数の実績」）。5 回を超えても合格しないときは、文書ではなく決まりかテンプレートに原因があるとみて、人に渡します。

合格したら、記録の先頭の表と「合格までの回数の実績」を更新します。

## 5. 決まりを育てる

複数の文書で同じ指摘が出たら、文書ではなく決まりかテンプレートを直します。docs/README.md の「書き方」の表に例を足す、テンプレートの `> 書くこと:` を具体的にする、のどちらかです。変えたら docs/README.md の最終確認日を更新します。

決まりは、評価と修正を回している途中では変えません。途中で変えると、それまで合格していた文が新しい決まりで引っかかり、評価が終わらなくなるためです。「決まり側の課題」は記録にためておき、対象の文書がすべて合格してからまとめて決まりに反映します。決まりを変えたら、影響する文書を全文評価し直します。

## 6. PR に書くこと

PR 本文の「テスト内容」に、文書ごとに「何回で合格したか」「残した指摘の件数」を書き、記録ファイルにリンクします。
