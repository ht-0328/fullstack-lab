# 設計の文書を書く

設計の文書は、実装する人（人でも AI でも）が追加の質問なしに着手でき、あとから読む人が「この部分は今どう作られているか」を 1 本で確かめられるようにするためのものです。そのために、文書は小さく保ち、決まったことだけを書きます。

文書の形の決まりは、このスキルには書き写していません。正は次の 2 つで、書く前に必ず読みます。片方だけが更新されて食い違うのを防ぐためです。

- [docs/design/README.md の「文書の単位と書き方」](../../../docs/design/README.md#文書の単位と書き方): 1 本の単位、題名と見出し、全体像（`README.md`）の構成、流れの図の置き方、書かないもの
- [docs/README.md の「書き方」と「形式の決まり」](../../../docs/README.md#書き方人が読める文書にする決まり): 文の書き方（W-1〜W-10）と形式（F-1〜F-6）

## 進め方

### 1. 課題の issue を確かめる

変更は集約リポジトリの issue から始めます。進み具合と決まっていないことの置き場所を、文書の外に 1 つ決めておくためです。

- `gh issue list -R ht-0328/fullstack-lab` で、この変更の issue を探します。
- 無ければ [課題のテンプレート](../../../.github/ISSUE_TEMPLATE/issue.md) の節（課題、決めること、やること、閉じる条件）に沿って起票します。起票は外への操作なので、本文をユーザーに見せてから `gh issue create -R ht-0328/fullstack-lab --body-file <ファイル>` を実行します。

### 2. 変わる文書を洗い出す

変わるフォルダの全体像（`docs/design/<フォルダ>/README.md`）の「文書の一覧」と「処理の流れ」、[docs/architecture/](../../../docs/architecture/README.md)、関係する契約（各領域の `openapi/*.yaml`）を読み、次の 3 つを一覧にします。

- 直す文書（今の作りが変わるもの）
- 足す文書（新しく作るもの。エンドポイント 1 つ、横断の仕組み 1 つ、DB の表、画面 1 つ、AWS のリソースか道具 1 つにつき 1 本）
- 全体像で直す箇所（「文書の一覧」の行、「処理の流れ」のシーケンス図）

1 つの変更は、たいてい複数のフォルダの文書にまたがります。たとえば操作を 1 つ足すなら、`api/` のエンドポイント、`authz/` の「操作ごとの可否」と設定、`web/` の BFF のエンドポイントと画面、`shared/` のスモークテストが変わります。洗い出した一覧をユーザーに見せてから書き始めると、抜けと書きすぎを早く直せます。

### 3. 文脈を集め、節ごとに書く

新しい文書を書くとき、または中身が大きく変わるときは、Anthropic の公式スキル **`example-skills:doc-coauthoring`**（文脈の収集、節ごとの推敲、読者テストの 3 段で文書を書く手順）を Skill ツールで呼び、その段取りで進めます。自己流で一気に書くと、書き手だけが知っている前提が文書から抜けやすいためです。そのスキルが使えない環境では、[references/coauthoring.md](references/coauthoring.md) の要約に沿って同じ 3 段を踏みます。

このリポジトリでは、公式スキルの段取りに次の 3 点を重ねます。

- **型は決まっています。** 「どんな構成にするか」は聞かず、同じフォルダの同じ種類の文書（エンドポイントならエンドポイントの文書）を例にして、節の見出しを揃えます。聞くのは中身（何を作るか、失敗したらどうするか、何で確かめるか）だけです。
- **決まっていないことは文書に書きません。** 推測で埋めず、issue の「決めること」に、判断に必要な情報と決める人を付けて書き、ユーザーに質問として出します。決まったら、その中身だけを本文に書きます。「決めること」が残っているうちは実装を始めません。
- **作る順序と進み具合も文書に書きません。** その変更の PR の分け方、作業の段取り、どこまで済んだかは、issue の「やること」のチェックリストに書きます。文書は実装が進んでも書き換えずに済む形に保ちます。

小さな直し（値を 1 つ変える、行を 1 つ足す）なら、公式スキルを呼ばずに直接直して構いません。

### 4. 流れの図を合わせる

誰が誰をどの順に呼ぶかが変わったら、全体像の節「処理の流れ」のシーケンス図（mermaid）を直します。新しい操作を足したら、図を 1 枚足します。図の置き方と描き方は [references/diagrams.md](references/diagrams.md) にあります。文は合っているのに図だけが古い、という状態がいちばん読者を迷わせるので、本文を直したら図も同じ変更で直します。

### 5. 確かめる

1. `python3 scripts/doc-lint.py` を実行し、0 件にします（先頭の表、リンク切れ、1 段落の文数を機械で確かめます）。
2. 読者テストをします。文脈を持たないサブエージェントに、直した文書だけを渡し、読者が聞きそうな質問（例: 「拒否されたとき画面には何が出るか」「この値はどこで設定するか」）に答えさせます。答えられない、または間違える質問があれば、文書に前提が足りていません。これは公式スキルの 3 段目と同じ手順です。
3. [writing-docs](../writing-docs/SKILL.md) の「評価する」以降の手順で、`doc-review` エージェントに決まりどおりかを評価させ、合格させます。
4. 書いた内容が今の実装を説明している部分（既にあるものの書き直し、文書の分割）は、`design-review` エージェントで実装と照らします。これから作るものは、実装のあとで照らします（[implementing-from-design](../implementing-from-design/SKILL.md) の仕上げ）。

## この構成に固有の置き場所

次の表は、変更の種類ごとに、どのフォルダのどの文書に書くかを示します。

| 変わるもの | 書く場所 |
|---|---|
| 契約（`openapi/*.yaml`）のエンドポイント | そのエンドポイントの文書に、処理と応答を書く。項目の一覧は契約にあるので書き写さない。互換か非互換か、バージョンの上げ方は `shared/contract-versioning.md` の決まりに従い、呼び出し側の追従の順序は issue の「やること」に書く |
| 認可の操作（`task:xxx`） | `authz/action-permissions.md` と `authz/settings.md`、BFF の側は `web/authz-decision-call.md` と、その操作を問い合わせるエンドポイントの文書 |
| 画面 | `web/screen-*.md`。画面 1 つにつき 1 本 |
| 入口、前段、Compose、スモークテスト、生成と配布 | `shared/` の該当する文書 |
| AWS のリソース、道具 | `infra/` の該当する文書。AWS のリソースを実際に作る前に、構成と費用の見込みをユーザーに示す |
| テスト | 各文書の節「テスト」に、どの層（単体、Karate、Playwright）で何を確かめるかを書く。スモークテストで確かめることは `shared/smoke-test.md` に書き、各文書からはスモークテストのまとまりの名前で指す |
| 方針とその理由、検討した案の比較 | 設計の文書ではなく ADR（[docs/adr/TEMPLATE.md](../../../docs/adr/TEMPLATE.md)）。使い分けは [docs/README.md](../../../docs/README.md#設計の文書と-adr-の使い分け) |

## 守ること

- **1 本に書くのは、作るもの 1 つです。** 書いているうちに 2 つ目が混ざったら、文書を分け、全体像の「文書の一覧」に行を足します。長い 1 本は、読者が要る部分を探す手間と、実装が変わったときに直す範囲の両方を増やします。
- **同じ事実を 2 本に書きません。** 片方に書き、もう片方からリンクします。2 か所にあると、片方だけが直されて食い違います。エンドポイントごとの応答、スモークテストで確かめること、architecture との分担のように、どちらを正にするかが決まっているものは、[「文書の単位と書き方」](../../../docs/design/README.md#文書の単位と書き方) の表にあります。
- **題名、見出し、表の列名は、書いてあるものの名前で書きます。** 「〜の返し方」「確かめ方」「〜のとき」や問いかけの形は、中身を言い表さず文書が稚拙に見えるので使いません（「エラー応答」「確認の方法」「401 の扱い」のようにします）。同じ種類の文書では見出しを揃えます。
- **語の一言は、フォルダの全体像に 1 回書きます。** 用語の表にある語と、全体像で一言をそえた語は、個別の文書で繰り返さなくて構いません。短い文書すべてに同じ一言が並ぶのを避けるためで、その代わり個別の文書は導入で全体像へリンクします。新しい語を使うときは、全体像の「このフォルダで使う語」に足します。
- **業務環境の事実と、学習用の仮定を分けます。** 不確かな点は「仮定」と書き、仮定に頼る箇所に [architecture の「仮定」](../../../docs/architecture/README.md#仮定) の番号を 1 回付けます。
- **既存の文書と矛盾したら、どちらが正かを勝手に決めません。** 実装を読んで確かめ、それでも決まらなければ矛盾点としてユーザーに報告します。
- **文書にコードは書きません。** 設定の抜粋と mermaid の図は書いて構いません。

## 出力

直した文書と足した文書（`docs/design/<フォルダ>/<作るものの名前>.md`）、行と図を合わせた全体像の `README.md`、「決めること」と「やること」を更新した issue。ユーザーへの報告には、変えた文書の一覧、issue に書いた「決めること」、確かめた結果（lint、読者テスト、`doc-review`）を書きます。
