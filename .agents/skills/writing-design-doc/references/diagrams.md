# 流れの図の置き方と描き方

設計の文書の図は mermaid で描きます。GitHub と VS Code のプレビューがそのまま表示でき、文と同じ差分で直せるためです。決まりの正は [docs/design/README.md の「文書の単位と書き方」](../../../../docs/design/README.md#文書の単位と書き方) の「流れの図」「仕組みの作りとしての順序」「全体像の図に描く範囲」「図と本文」「図と重なる文」「図と文や表の両方があってよい場合」の行で、ここにはその描き方の細部を書きます。

## どこに置くか

| 図の種類 | 置く場所 | 理由 |
|---|---|---|
| 誰が誰をどの順に呼ぶか（`sequenceDiagram`） | 全体像（`README.md`）の節「処理の流れ」。主な操作ごとに小見出し（`###`）を立て、1 枚ずつ | 1 つの操作は複数の文書にまたがるので、個別の文書に散らばると流れが 1 枚で追えない |
| その文書だけの判定や分岐（`flowchart`） | 個別の文書 | 判定の中身は、その文書を読む人だけが要る |
| 構成（何が何につながっているか。`flowchart`） | 全体像の先頭か、[docs/architecture/](../../../../docs/architecture/README.md) | 領域をまたぐ構成は architecture が正。同じ図を書き写さずリンクする |

個別の文書には、全体像に置いたシーケンス図と同じ図を置きません。導入の段落の後に「流れは [全体像の「〜」](README.md#〜) の図にある。」と書いてリンクします。

## 描き方

- 図の直前に「次の図は、〜の流れを示す。」の 1 文を置き、図の後に、細部を書いた個別の文書へのリンクを 1 文で置きます。
- 参加者は本文の呼び名にします（ブラウザ、入口、前段、Nuxt、BFF、認可 API、API、認証 API、Keycloak、DB、外部サービス、開発者、Actions など）。1 枚の参加者は 6 つくらいまでにし、超えるなら手前をまとめます（例: BFF より手前を「呼び出し元」にする）。
- メッセージは短く、呼ぶ先のパスか操作の名前と、応答のステータスコードを書きます。ヘッダー名、設定の値、ログのレベル、応答の項目の値は図に入れず、個別の文書の本文に書きます。
- 分岐は主なものだけを `alt` / `opt` で入れます（拒否、404、503、縮退など）。
- 図にした順序を、同じフォルダの箇条書きや段落でもう一度言いません。箇条書きには、各段の理由、値、条件を書きます。依存の関係のような順序でない図と表が同じ事実になったら、片方だけを残します。

## 構文で壊れやすい点

描画の失敗は、文書を開くまで気づけません。次の点を守ると、ほとんど防げます。

- `flowchart` のノードのラベルと矢印のラベルは、`A["..."]`、`-->|"..."|` のように引用符で囲みます。括弧、`{id}`、コロンが入るラベルは、囲まないと壊れます。
- `sequenceDiagram` の参加者は `participant` で先に宣言します。メッセージに `;` と `#` を入れません。
- `alt` / `opt` / `loop` は `end` で閉じます。

図を足したり直したりしたら、VS Code の Markdown のプレビューで表示を確かめます。
