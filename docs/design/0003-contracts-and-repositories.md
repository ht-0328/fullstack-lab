## 解決する課題

業務環境と同じく、領域ごとに別リポジトリで開発し、領域同士を OpenAPI の契約と配布された成果物だけでつなぐ。

| 項目 | 内容 |
|---|---|
| 対象 | 画面 ⇄ BFF、BFF ⇄ API、BFF ⇄ 認可 API の 3 つの境界 |
| 発生規模 | リポジトリ 4 つ（集約 1 + 領域 3） |
| 読者への影響 | 契約を変えたときの影響範囲と順序が決まっており、他の領域のソースを読まなくても開発できる |
| 成功条件 | 各リポジトリの CI が単独で通る。集約の CI でサブモジュールを含めた全体が動く。同じバージョンの成果物が上書きされない |

## 制約と前提

| 区分 | 内容 | 根拠 |
|---|---|---|
| 制約 | 画面と BFF は同じリポジトリ、API は領域ごとに独立 | 業務環境の事実 |
| 制約 | 生成コードはコミットしない（2026-10-28 に変更: 業務環境では生成コードを git で管理していると分かり、[ADR-0003](../adr/ADR-0003-commit-generated-code.md) で git 管理に切り替えた。食い違いは Docker の `check-generated` ステージで防ぐ） | 仕様と生成物の食い違いを防ぐ |
| 制約 | 同じバージョンの成果物を上書きしない | CodeArtifact と同じ運用にする |
| 前提 | 画面側は型・DTO を OpenAPI から生成し、BFF を呼ぶクライアントは自前だった | 業務環境の事実 |
| 仮定 | 業務では API クライアントを成果物として配布していた | [構成の仮定 10](../architecture/README.md#仮定) |

## 採用案

| 要素 | 採用内容 | 責務 |
|---|---|---|
| リポジトリ | 集約（`fullstack-lab`）が `web` / `api` / `authz` を git submodule で参照 | 集約は Compose・入口・ドキュメント。領域は自分のビルドとテスト |
| 契約 | 各領域の `openapi/*.yaml`。`info.version` で版を管理 | 境界の唯一の定義 |
| 提供側の生成 | `openapi-generator`（`kotlin-spring`、`interfaceOnly`） | コントローラーのインターフェースと DTO。実装が仕様に従う |
| 利用側（Kotlin） | 提供側が `kotlin`（`jvm-spring-restclient`、Jackson 3）でクライアントを生成し、Maven 成果物として publish。BFF がバージョンで依存 | 利用側は提供側のソースを見ない |
| 利用側（画面） | `openapi-typescript` で型だけ生成し、`openapi-fetch` の型付きクライアントで呼ぶ | HTTP の層は Nuxt / fetch に任せる（[ADR-0001](../adr/ADR-0001-nuxt-generates-types-only.md)） |
| 配布 | ローカル: Reposilite、CI: GitHub Packages、AWS: CodeArtifact。環境変数で切り替え | [ADR-0002](../adr/ADR-0002-distribute-clients-as-artifacts.md) |
| 閲覧 | Swagger UI（入口の `/swagger/`、ログイン後） | 3 つの仕様を 1 画面で |
| CI | 領域: 単体テスト + Karate、main で publish。`web`: 型チェック + BFF 単体。集約: Compose でスモーク + Karate + Playwright | 各リポジトリが単独で通る |

### 契約を変えるときの順序

提供側（仕様と `version` を同時に上げる → 生成して実装 → PR → マージで publish）→ 利用側（`gradle.properties` のバージョンを上げる → 実装 → PR）→ 集約（参照更新）。手順はスキル `updating-openapi-contract`。

## 比較した代替案とトレードオフ

| 案 | 利点 | 欠点 | 採否の理由 |
|---|---|---|---|
| git submodule で実際に分割する（採用） | 業務と同じ境界。各リポジトリの CI が独立 | コミットと PR が増える。参照更新の手間 | 利用者の判断 |
| 単一リポジトリでディレクトリ分割 | 手間が少ない。後から `subtree split` で分けられる | 境界が「約束」でしか守られない | 不採用（提案はした） |
| BFF 側で API の仕様からクライアントを生成する | publish の仕組みが要らない | BFF が API の仕様ファイルを参照する経路が要る。版の管理が BFF 任せになる | 不採用。成果物の配布を学ぶ |
| 画面側で HTTP 層まで生成する（`typescript-fetch` など） | 呼び出しコードを書かなくてよい | Nuxt の SSR と二重になり、ヘッダーの転送を包み直す | 不採用（ADR-0001） |

## 失敗時の動作

| 失敗条件 | 検知方法 | システムの動作 | 利用者への影響 |
|---|---|---|---|
| 仕様と実装がずれる | 生成インターフェースの実装がコンパイルできない | ビルドが失敗する | 取り込めない |
| `info.version` と `version` がずれる | `checkSpecVersion` | publish が失敗する | 取り込めない |
| 同じバージョンを再 publish | スクリプト / CI が存在を確認 | 何もしない | なし |
| Maven リポジトリに到達できない | BFF のビルドで依存解決が失敗 | ビルドが失敗する。ローカルは `publish-clients.sh` の実行を促す | 起動できない |
| 利用側が古いバージョンのまま | なし（意図的） | 古い契約で動き続ける | 新しい項目が使えないだけ |

## 技術観点の確認

該当しない観点は行ごと削り、該当しない理由を 1 行書いている（[docs の決まり](../README.md#共通の決まり)）。

### セキュリティと権限

| 観点 | 内容 |
|---|---|
| 秘密情報の保管 | Maven リポジトリの資格情報は環境変数と build secret で渡し、イメージに残さない |
| 認可 | publish はトークン（Reposilite）/ `packages: write`（GitHub）。取得は匿名（Reposilite）/ `packages: read` |

### 展開と後始末

| 観点 | 内容 |
|---|---|
| 互換性 | 項目の追加は互換。必須項目の追加・削除・型変更は非互換でメジャーを上げる。古い成果物は残す |
| 廃止計画 | Reposilite と GitHub Packages は CodeArtifact 導入後も学習用に残す |

データ、性能と可用性、可観測性は該当しない（配布の仕組みのため）。
