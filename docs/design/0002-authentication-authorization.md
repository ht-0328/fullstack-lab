## 解決する課題

業務環境の「ALB を経由し、認証を通過すると画面や BFF に届く」「社員は Okta、一般利用者は Keycloak」「JWT」「BFF が認可 API を呼ぶ」という構成を、ローカルで動かして学べる形にする。

| 項目 | 内容 |
|---|---|
| 対象 | ログイン、セッション、JWT の検証、認可の判定、ログアウト |
| 発生規模 | 学習用。利用者 4 人（テストユーザー） |
| 読者への影響 | 認証と認可の責務の分かれ目を、動く構成で確かめられる |
| 成功条件 | 未認証は入れない。偽のトークンは入口でも BFF でも拒否される。一般利用者は自分のデータだけ、社員はロールどおりに操作できる。ログアウトで IdP のセッションも終わる |

## 制約と前提

| 区分 | 内容 | 根拠 |
|---|---|---|
| 制約 | ALB の認証機能はローカルで動かない。代替手段が要る | AWS のマネージド機能 |
| 制約 | Okta はローカルで動かない。代替手段が要る | SaaS |
| 前提 | 社員は Okta、一般利用者（マイページ）は Keycloak で認証していた | 業務環境の事実（利用者の説明） |
| 前提 | トークンは JWT で、BFF が認可 API を呼んでいた | 業務環境の事実（利用者の説明） |
| 仮定 | ALB はホスト名ごとに IdP を分け、BFF は ALB が転送する IdP のアクセストークンを検証する | [構成の仮定 2・3](../architecture/README.md#仮定) |

## 採用案

前段が認証とセッションを担い、BFF がトークンを検証し、認可 API が可否を判定する。

| 要素 | 採用内容 | 責務 |
|---|---|---|
| 入口 | Nginx（`auth_request`） | ホスト名で利用者の種別を分け、未認証を前段へ回す。ALB と同じヘッダー名でトークンを後段へ渡す。クライアントが送った同名ヘッダーは上書きする |
| 前段認証（ALB の代替） | oauth2-proxy × 2（customer / staff） | IdP へのリダイレクト、コールバック、暗号化 Cookie、トークン更新、ログアウト |
| IdP | Keycloak。realm `customer`（一般利用者）と realm `staff`（Okta の代替。`groups` クレームを出す） | 認証とトークンの発行 |
| BFF | Spring Security（リソースサーバー） | `x-amzn-oidc-accesstoken` の JWT を検証（署名・`iss`・`aud`・`exp`）。発行元ごとのクレームの違いを `CurrentUser` に吸収 |
| 認可 API | 独立サービス | 主体（種別、ロール）・操作・対象（所有者）から可否を判定 |
| 画面 | Nuxt | `/bff/me` の `capabilities` で出し分け。守りではない |

### 影響するリポジトリ

`web`（BFF の SecurityConfig、`CurrentUserFactory`、`AuthzClient`、画面の出し分け）、`authz`（全体）、集約（Nginx、oauth2-proxy、Keycloak の realm）。`api` は変えない（BFF を信頼し、ヘッダーで利用者を受け取る）。

### 認可の方針

| 主体 | 判定 |
|---|---|
| 一般利用者 | 許可された操作のうち、自分が所有する対象だけ |
| 社員 | ロール（Okta のグループ名）に付いた操作なら、所有者を問わず |
| どれにも当てはまらない | 拒否（既定で拒否） |

ロールの付与は IdP、ロールごとの権限は認可 API の設定が持つ。

## 比較した代替案とトレードオフ

| 案 | 利点 | 欠点 | 採否の理由 |
|---|---|---|---|
| oauth2-proxy で ALB の認証を模擬する（採用） | ログイン画面・Cookie・トークン更新まで再現でき、アプリ側のコードが AWS と同じになる | コンテナが 2 つ増える | ALB との差分を小さくできる |
| Nginx が固定の利用者ヘッダーを付ける（第 1 段階で採用していた） | 最も単純 | ログインの流れと JWT の検証を学べない | 認証を学ぶ段階で置き換えた |
| BFF 自身が OAuth2 クライアントになる | 前段が要らない | ALB の構成と責務の分かれ目が変わる。セッションを BFF が持つ | 不採用 |
| API でも JWT を検証する（多層防御） | BFF が破られても API が守る | API に認証の知識が入る。学習の範囲が広がる | 今回は不採用。発展課題として明記 |

## 失敗時の動作

| 失敗条件 | 検知方法 | システムの動作 | 利用者への影響 |
|---|---|---|---|
| IdP が停止 | oauth2-proxy のリダイレクト先が応答しない | ログインできない。既存のセッションはトークン更新に失敗した時点で無効になる | 復旧まで使えない |
| BFF が公開鍵を取得できない | `NimbusJwtDecoder` の例外 | 401 | ログイン済みでも使えない |
| 偽のトークンヘッダー | Nginx が上書き。BFF が署名を検証 | 401 | なし（拒否される） |
| 認可 API が停止 | BFF の `AuthzClient` | 503。許可しない（fail-closed） | 操作できない |
| アクセストークンの期限切れ（5 分） | oauth2-proxy が 4 分ごとに更新 | 新しい Cookie を Nginx 経由で返す | なし |

## 技術観点の確認

該当しない観点は行ごと削り、該当しない理由を 1 行書いている（[docs の決まり](../README.md#形式の決まり)）。

### セキュリティと権限

| 観点 | 内容 |
|---|---|
| 認証 | OIDC（認可コード + PKCE）。アクセストークンは JWT |
| 認可 | 認可 API。既定で拒否 |
| 秘密情報の保管 | クライアントシークレット、Cookie の暗号化キーは `.env`。realm の JSON はプレースホルダーで受け取る |
| 通信の暗号化 | ローカルは HTTP のため該当しない。Cookie は `Secure` なし。AWS では ALB が TLS を終端し、Cookie は `Secure` になる |
| ヘッダーの偽装 | 前段（Nginx / ALB）が上書きし、BFF が署名も検証する二重の守り。BFF に前段以外から届かないことが前提（AWS ではセキュリティグループ） |
| CSRF | セッション Cookie を持つのは前段だけ（`SameSite=Lax`）。BFF は JSON しか受け付けず、自身はセッションを持たないため CSRF トークンは使わない |
| 監査ログ | 認可 API が主体・操作・対象・結果・理由を記録 |

### データ

| 観点 | 内容 |
|---|---|
| 扱う個人情報 | IdP の `sub`、表示名。トークンは Cookie に暗号化して保持し、DB には保存しない |
| 保持期間と削除 | Cookie は 8 時間。Keycloak は開発モードで、コンテナを作り直すと初期化される |

移行と容量は該当しない。

### 性能と可用性、可観測性

学習用のため目標値は置かない。公開鍵は BFF がキャッシュする。

### 展開と後始末

| 観点 | 内容 |
|---|---|
| 展開手順 | realm の変更は `docker compose up -d --force-recreate keycloak` |
| 互換性 | ヘッダー名は ALB と同じ（`x-amzn-oidc-accesstoken` など）。AWS 化でアプリ側は変えない |
| ローカルと AWS の差分 | [ロードマップ「ALB の認証」](../roadmap/README.md#alb-の認証) |
