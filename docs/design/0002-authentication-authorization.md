## 解決する課題

この設計書は、業務環境（作成者が以前いた職場。このリポジトリはその構成を学習用に再現している。[用語](../architecture/README.md#用語)）の認証と認可の構成を、ローカルで動かして学べる形にする変更を記す。[ロードマップのフェーズ 1](../roadmap/README.md#フェーズ) では、入口（すべてのリクエストを最初に受けて振り分けるもの。ローカルは Nginx、AWS では ALB）が固定の利用者ヘッダーを付けるだけで、ログインの流れと JWT（署名付きのトークン。発行元の公開鍵で検証できる）の検証を学べなかった。この設計書は、誰が認証し、誰が JWT を検証し、誰が認可を判定するかを決める。

業務環境では、画面と BFF（Backend for Frontend。画面専用のサーバー側 API で、API と認可 API を呼ぶ）へのリクエストは、ALB（AWS のロードバランサー。業務環境では認証も担っていた）の認証を通過してから届いていた。社員は Okta、一般利用者は Keycloak という 2 つの IdP（Identity Provider。ログインを受け付けてトークンを発行するサービス）で認証し、BFF は JWT を受け取って認可 API に可否を問い合わせていた。

次の表は、この変更の対象と規模、何ができれば成功かをまとめる。

| 項目 | 内容 |
|---|---|
| 対象 | ログイン、セッション、JWT の検証、認可の判定、ログアウト |
| 発生規模 | リポジトリ 3 つ（`web`、新設の `authz`、集約リポジトリ）。利用者は学習用のテストユーザー 4 人（一般利用者 2 人、社員 2 人） |
| 利用者への影響 | 今は入口が固定の利用者ヘッダーを付けるだけで、ログインの流れと JWT の検証を動かして確かめられない |
| 成功条件 | 未認証は入れない。偽のトークンは入口でも BFF でも拒否される。一般利用者は自分のデータだけ、社員はロールどおりに操作できる。ログアウトで IdP のセッションも終わる |

## 採用案

前段（アプリより手前で認証とセッションを担う層。ローカルでは oauth2-proxy、AWS では ALB の認証アクション）が認証とセッションを担い、BFF がトークンを検証し、認可 API が可否を判定する。

次の表は、採用案を要素ごとに分け、何を採用し、何を担当させるかを示す。realm は Keycloak の中で利用者と設定を分ける単位、クレームはトークンに含まれる属性（利用者の ID やロールなど）で、`auth_request` はリクエストごとに oauth2-proxy へ認証の確認を問い合わせる Nginx の機能である。

| 要素 | 採用内容 | 責務 |
|---|---|---|
| 入口 | Nginx（`auth_request`） | ホスト名で前段（oauth2-proxy）を選び、未認証を前段へ回す。利用者の種別はホストではなく、BFF が JWT の発行元 `iss` から判断する。ALB と同じヘッダー名でトークンを後段へ渡す。クライアントが送った同名ヘッダーは上書きする |
| 前段認証（ALB の代替） | oauth2-proxy（OpenID Connect のログインを代行するプロキシ）× 2（customer / staff） | IdP へのリダイレクト、コールバック、暗号化 Cookie、トークン更新、ログアウト |
| IdP | Keycloak。realm `customer`（一般利用者）と realm `staff`（Okta の代替。`groups` クレームを出す） | 認証とトークンの発行 |
| BFF | Spring Security（リソースサーバー。受け取ったトークンを検証して API を守る側） | `x-amzn-oidc-accesstoken` の JWT について、署名と、発行元 `iss`・宛先 `aud`・期限 `exp` を検証する。発行元（realm）ごとのクレームの違いを `CurrentUser`（BFF の中で使う利用者情報。ID、名前、種別、ロール）に吸収する |
| 認可 API | 独立サービス | 主体（種別、ロール）・操作・対象（所有者）から可否を判定 |
| 画面 | Nuxt（Vue の画面フレームワーク） | `/bff/me` の `capabilities` でボタンや項目を出し分ける。出し分けは見た目のためで、守りは BFF と認可 API が担う |

### 認可

次の表は、主体の種別ごとに認可 API がどう判定するかを示す。一般利用者は所有者かどうかで、社員はロールで決まる。

| 主体 | 判定 |
|---|---|
| 一般利用者 | 許可された操作のうち、自分が所有する対象だけ |
| 社員 | ロール（Okta のグループ名）に付いた操作なら、所有者を問わず |
| どれにも当てはまらない | 拒否（既定で拒否） |

ロールの付与は IdP（realm `staff` の `groups` クレーム）が、ロールごとの権限は認可 API の設定（`authz/src/main/resources/application.yml` の `staff-role-permissions`）が持つ。社員のロールは `task-viewer`（閲覧だけ）と `task-admin`（閲覧に加えて登録などの変更もできる）の 2 つで、操作ごとの可否の一覧は [architecture/ の「認可の流れ（タスク詳細の例）」](../architecture/README.md#認可の流れタスク詳細の例) の表にある。

### テスト

次の表は、層ごとに何を確かめるかを示す。Karate は API を HTTP で呼んで確かめるテスト、スモークは集約リポジトリで全体を起動して主要な経路を通すテストである。認証の守りは画面ではなく、入口と BFF に直接送って拒否されることで確かめる。

| 層 | 対象 | 確かめること |
|---|---|---|
| 単体 | BFF の `CurrentUserFactory`（`CurrentUserFactoryTest`） | realm `customer` の `realm_access.roles` と realm `staff` の `groups` という、場所の違うロールのクレームから、同じ形の `CurrentUser` を作る |
| 単体 | BFF の `TaskViewService`（`TaskViewServiceTest`） | 認可 API が 503 を返すと失敗する（fail-closed。判定できないときは拒否する）。認可で拒否されたら API を呼ばない。他の一般利用者のタスクは 404 で存在を隠す |
| Karate | 認可 API（`authz/karate/features/decisions.feature`） | 一般利用者は本人の対象だけ許可され、他人の対象と全件の一覧は拒否される。社員は `task-viewer` と `task-admin` のロールどおりに判定される。未知のロールとロールの無い社員は拒否される。契約に無い `userType` と `subject` の欠落は 400 |
| スモーク | 集約リポジトリの `scripts/smoke-test.sh` の未認証とトークンの偽装（入口から BFF まで） | 未認証の画面は 302 でログインへ、未認証の BFF は 401 になる。偽のトークンヘッダーは、未認証なら 401 になり、ログイン後は入口が上書きする。署名の無い JWT をコンテナ内から BFF に直接送ると 401 になる |
| スモーク | 集約リポジトリの `scripts/smoke-test.sh` のログインとログアウト（入口から BFF、認可 API まで） | 社員は `groups` クレームからロールを得る。一般利用者のセッションは管理画面（社員用のホスト `admin.localhost`）で使えない。ログアウト後の BFF は 401 になり、IdP のセッションも終わって再びログインフォームが出る |

画面（Playwright）で確かめることは、この設計書では挙げない。認証と認可の守りは入口と BFF、認可 API にあり、表の単体、Karate、スモークの行で確かめるためである。

## 比較した代替案とトレードオフ

次の表は、検討した案を採用案も含めて並べ、採否の理由を示す。

| 案 | 利点 | 欠点 | 採否の理由 |
|---|---|---|---|
| oauth2-proxy で ALB の認証を模擬する（採用） | ログイン画面・Cookie・トークン更新まで再現でき、アプリ側のコードが AWS と同じになる | コンテナが 2 つ増える | ALB との差分を小さくできる |
| Nginx が固定の利用者ヘッダーを付ける（[ロードマップのフェーズ 1](../roadmap/README.md#フェーズ) で採用していた） | 最も単純 | ログインの流れと JWT の検証を学べない | 不採用。ログインの流れと JWT の検証を学べないため、認証を学ぶフェーズ 1.5 で置き換えた |
| BFF 自身が OAuth2 クライアントになる | 前段が要らない | ALB の構成と責務の分かれ目が変わる。セッションを BFF が持つ | 不採用。業務環境では前段（ALB）が認証を担っており、その責務の分かれ目を再現するため |
| API でも JWT を検証する（多層防御） | BFF が破られても API が守る | API に認証の知識が入る。学習の範囲が広がる | 今回は不採用。業務環境と同じく BFF が認可 API を呼ぶ構成を先に再現する。API での検証は「課題・申し送り事項」に残す |

## 失敗時の動作

次の表は、失敗の条件ごとに、どう検知し、システムがどう動き、利用者にどう見えるかを示す。認可 API の失敗は拒否（fail-closed）が既定である。

| 失敗条件 | 検知方法 | システムの動作 | 利用者への影響 |
|---|---|---|---|
| IdP が停止 | oauth2-proxy のリダイレクト先が応答しない | ログインできない。既存のセッションはトークン更新に失敗した時点で無効になる | 復旧まで使えない |
| BFF が公開鍵を取得できない | BFF の `NimbusJwtDecoder`（Spring Security の JWT の検証器）が例外を出す | BFF が 401 を返す | ログイン済みでも使えない |
| 偽のトークンヘッダー | 入口（Nginx）が同名ヘッダーを上書きし、BFF が署名を検証する | 未認証なら入口が 401 を返す（画面は 302 でログインへ）。ログイン済みなら入口が本物のトークンで上書きするので、偽のトークンは BFF に届かない。入口を通らず BFF に直接届いた偽のトークンは、BFF が署名を検証して 401 を返す | なし。偽のトークンは使われない |
| 認可 API が停止 | BFF の `AuthzClient` の呼び出しが失敗する | 503。許可しない（fail-closed） | 操作できない |
| アクセストークンの期限切れ（5 分。realm の JSON の `accessTokenLifespan` が 300 秒） | oauth2-proxy が 4 分ごとに更新する（`compose.yaml` の `OAUTH2_PROXY_COOKIE_REFRESH`。期限の 5 分が切れる前に更新するため） | 新しい Cookie を Nginx 経由で返す | なし |

### セキュリティと権限

次の表は、セキュリティの観点ごとに、この構成での扱いを示す。

| 観点 | 内容 |
|---|---|
| 認証 | OIDC（OpenID Connect）の認可コードフローに、PKCE（認可コードを横取りされても使えなくする仕組み）を加えて使う（`compose.yaml` の `OAUTH2_PROXY_CODE_CHALLENGE_METHOD` が `S256`）。アクセストークンは JWT である |
| 認可 | 認可 API。既定で拒否 |
| 秘密情報の保管 | クライアントシークレット、Cookie の暗号化キーは `.env` に置く。realm の JSON（`keycloak/import/staff-realm.json`、`auth/keycloak/import/customer-realm.json`）には `${STAFF_CLIENT_SECRET}` のようなプレースホルダーを置き、Keycloak が起動時に環境変数で置き換える |
| 通信の暗号化 | ローカルは HTTP のため該当しない。Cookie は `Secure` なし。AWS では ALB が TLS を終端し、Cookie は `Secure` になる |
| ヘッダーの偽装 | ローカルでは入口（Nginx）、AWS では ALB がヘッダーを上書きし、BFF が署名も検証する二重の守り。BFF に入口以外から届かないことが前提（AWS ではセキュリティグループ（通信を許す相手を絞る AWS の設定）で守る） |
| CSRF | CSRF（別サイトから利用者のセッションで勝手に送信させる攻撃）への対策に、CSRF トークンは使わない。セッション Cookie（`SameSite=Lax`）を持つのは前段だけで、BFF は自身のセッションを持たず、JSON しか受け付けないためである |
| 監査ログ | 認可 API が主体・操作・対象・結果・理由を記録 |

### データ

次の表は、データの観点ごとの扱いを示す。

| 観点 | 内容 |
|---|---|
| 扱う個人情報 | IdP の `sub`（IdP が利用者ごとに振る ID のクレーム）、表示名。トークンは Cookie に暗号化して保持し、DB には保存しない |

### 性能と可用性、可観測性

学習用のため目標値は置かない。BFF はタスクの操作ごとに認可 API を 1 回呼び、未完了のタスクの詳細では完了ボタンの出し分け（`canComplete`）のためにもう 1 回呼ぶ。`/bff/me` は `capabilities` の 2 項目（タスクの登録とパスワード変更）のために 2 回呼ぶ。公開鍵は BFF がキャッシュする。

入口が付けたリクエスト ID（`X-Request-Id`）を、BFF は認可 API と API への呼び出しに引き継ぐ（`web/bff` の `InternalRestClient.kt`）。認可 API もこの ID をログに載せるので、サービスをまたいで 1 つのリクエストを追える。

次の表は、展開の手順と互換性、ローカルと AWS の差分の参照先を示す。

| 観点 | 内容 |

## 課題・申し送り事項

この変更に含めないことと、AWS 化（[ロードマップのフェーズ 5](../roadmap/README.md#フェーズ)。ALB の認証）に送ることを次に挙げる。

- API でも JWT を検証する多層防御は含めない。API は BFF を信頼する（[仮定 7](../architecture/README.md#仮定)）。発展課題として残す。
- `x-amzn-oidc-data`（ALB が署名する JWT）の検証は再現しない。ローカルの入口はこのヘッダーを空にして転送する。差分は [ロードマップ「ALB の認証」](../roadmap/README.md#alb-の認証) にある。
- AWS 上の Keycloak は ECS（AWS のコンテナ実行サービス）で自前運用する。2026-11-01 に作成者（ht-0328）が決めた。Cognito（AWS の IdP サービス）などで代用する案は、ローカルと違う製品になり、学んだ認証の仕組みが AWS につながらないので採らない。費用は常時稼働した場合で月約 25 ドルの見込みである（[ロードマップ「フェーズ」](../roadmap/README.md#フェーズ) の表のフェーズ 5）。
- 社員の IdP に本物の Okta（Developer アカウント）を使うかは決めていない。フェーズ 5 の着手前に作成者（ht-0328）が決める。必要なのはアカウントの用意で、使う場合も BFF の `staff` 発行元の設定を差し替えるだけでコードは変わらない（[ロードマップ「IdP の用意」](../roadmap/README.md#idp-の用意)）。
