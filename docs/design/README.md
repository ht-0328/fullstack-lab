この文書は、設計の文書の入口です。設計の文書は、各領域（独立したリポジトリで作るアプリの単位。[用語](../architecture/README.md#用語)）と、AWS のインフラ、領域をまたぐ仕組みが今どう作られているかを書いた文書です。この `design/` の下のフォルダ（`web/`、`api/`、`authz/`、`auth/`、`infra/`、`shared/`。まとめて「設計の文書のフォルダ」と呼ぶ）に、作るもの 1 つにつき 1 本を置きます。この文書には、文書の単位と書き方、変更するときの流れ、フォルダごとの全体像への案内を載せています。

方針とその理由は、設計の文書ではなく ADR（Architecture Decision Record。方針とその理由の記録。[ADR の索引](../adr/README.md)）に書きます。使い分けは、[docs の「設計の文書と ADR の使い分け」](../README.md#設計の文書と-adr-の使い分け)にあります。

## 文書の単位と書き方

設計の文書 1 本に書くのは、作るもの 1 つです。作るものは、エンドポイント 1 つ、画面 1 つ、仕組み 1 つ、DB の表、AWS のリソースか道具 1 つなどで、フォルダごとの単位は「フォルダごとの全体像」の節の表にあります。1 本を小さくするのは、読者が知りたい部分だけを開けるようにし、実装が変わったときに直す文書を 1 本に絞るためです。

次の表は、設計の文書の書き方の決まりを示します。文の書き方と形式は、[docs の「書き方」と「形式の決まり」](../README.md#書き方人が読める文書にする決まり)に従います。

| 決まり | 内容 |
|---|---|
| 題名 | 作るもの自体の名前にする（例: 「JWT の検証」「タスクの詳細（`GET /bff/tasks/{id}`）」）。「〜の設計書」は付けない |
| 題名、見出し、表の列名の言い回し | 書いてあるものの名前で書く。たとえ（例: 「〜との約束」）、問いかけ（例: 「〜か」「何を返すか」）、「〜方」で終わる語（例: 返し方、決め方、確かめ方、上げ方）、「〜とき」を含む言い回し（例: 「未認証のときの応答」）は使わない。良い例: 「呼び出し元と受け取るヘッダー」「エラー応答」「確認の方法」「401 の扱い」「空の可否」 |
| 言い回しの及ぶ範囲 | 言い回しの決まりは、題名、見出し、表の列名のほか、表の行名（1 列目の項目名）にも当てる。「A か B」のように並べる「か」は、問いかけに数えない |
| 見出しの揃え方 | 同じ種類の文書では見出しを揃える。エンドポイントの文書は「処理と応答」「テスト」とする。テストを持たないエンドポイント（例: 稼働の確認）は、節「テスト」を省いてよい。仕組みの文書の節「テスト」は、確かめるテストがあるときだけ置く |
| 確かめる方法の節 | スモークテストで確かめる仕組みと、手で確かめる仕組みの文書は、確かめる方法の節を「確認の方法」とする。テストや検査そのものを作るものとする文書（例: スモークテスト、CI）の「確かめること」のような節は、作るものの中身で、この行の節に当たらない。確かめる方法が無い文書は、節を置かなくてよい |
| 1 本に 1 つ | 1 本に 2 つ目の作るものが混ざったら、文書を分ける。変更の手順 1 つ（例: 操作とロールの追加）も、作るもの 1 つとして 1 本にしてよい。同じ事実を 2 本に書いた重なりは、W-9 で指摘する |
| 全体像の文書 | フォルダごとに `README.md` を 1 本置く。何をするものか、節「処理の流れ」、節「文書の一覧」、関連する文書へのリンクだけを書き、値や設定などの細かいことは個別の文書に書く。構成の図、そのフォルダにあるものの一覧、フォルダの文書すべてにかかる制約と前提、節「このフォルダで使う語」（「語の一言」の行）は、全体像に置いてよい |
| 文書の一覧 | 全体像の節「文書の一覧」は、「文書」と「内容」の 2 列の表にする。文書の種類（例: 仕組み、エンドポイント、画面）ごとに表を分けてよく、分けても列は同じにする |
| 語の一言 | [architecture の「用語」](../architecture/README.md#用語)の表にある語と、そのフォルダの全体像で一言をそえた語は、個別の文書で一言を繰り返さなくてよい。サービス名（API、認可 API、認証 API、BFF）も同じ扱いにする。全体像は、用語の表に無い語を節「このフォルダで使う語」の表にまとめてよい。個別の文書は、導入で全体像へリンクする |
| 語の表 | 全体像の節「このフォルダで使う語」の表の「意味」のセルにも、一言の書き方（[docs の「判定に迷うときの扱い」](../README.md#判定に迷うときの扱い)の W-2 の行）を当てる。全体像では、語の表にある語は、表より前の段落でも一言が要らない。architecture の「各サービスの役割」の表は一言の代わりにならないので、その表にしか無い語は語の表に書く。語の表の説明と同じ文が個別の文書に残っていても、W-9 の重なりには数えない |
| 流れの図 | 誰が誰をどの順に呼ぶかは、全体像の節「処理の流れ」に、主な操作ごとのシーケンス図（mermaid の `sequenceDiagram`）で描く。個別の文書には同じ図を置かず、全体像の図へリンクする。その文書だけの判定や分岐は、個別の文書にフローチャート（`flowchart`）で描いてよい。全体像の「処理の流れ」は、同じ図が [architecture](../architecture/README.md) にあるなら、その図へのリンクで代えてよい |
| 仕組みの作りとしての順序 | 仕組みの作りとしての順序（その仕組みを作る、変えるたびに同じになる順序。例: 「state のバケットを先に作る」「契約は提供側、利用側、集約リポジトリの順に変える」）は、人が行う操作や PR の順を含んでいても、全体像のシーケンス図と、個別の文書の本文、表、フローチャートに書いてよい。「書かないもの」の行の「作る順序」は、1 件の変更を進めるための PR の分け方と作業の段取り（issue の「やること」に書くもの）を指し、仕組みの作りとしての順序は当たらない |
| 全体像の図に描く範囲 | 誰が誰を呼ぶか、呼ぶ先のパスか操作の名前、応答のステータスコード、主な分岐までを描く。渡す値の名前（例: 「利用者の ID と名前を渡す」）までは描いてよい。ヘッダー名、設定の値、ログのレベル、応答の項目の値は、個別の文書に書く。Secret の名前、IAM の操作名、ファイルのパス、Dockerfile のステージ名も、個別の文書に書く |
| 図と本文 | 図の直前に、何の図かを 1 文で書く。図に描く名前、パス、ステータスコードは、そのフォルダの文書の本文や表と同じにする。順序と依存の関係は、図だけに描いてよい（「図と重なる文」の行） |
| 図と重なる文 | 図にした順序を、同じフォルダの箇条書きや段落でもう一度言わない（箇条書きには理由、値、条件を書く）。1〜2 文の要約と全体像の図へのリンクは書いてよい。順序でない図（依存の関係、生成物と置き場所）と表が同じ事実なら、片方だけにする |
| 図と文や表の両方があってよい場合 | 図の中身が 1〜2 文で言い切れるなら、要約の文と図の両方があってよい。分岐のフローチャートと、その分岐で確かめることの中身、値、理由を書いた表は、同じ事実の重なりに数えず、両方あってよい（例: JWT の検証の「流れ」の図と「確かめること」の表） |
| 先頭の表 | 置かない。題名の次を導入の段落にする（[docs の「判定に迷うときの扱い」](../README.md#判定に迷うときの扱い)の F-2 の行） |
| 書く中身 | 作るものと作り方、その作りにする理由、失敗時の動作、テスト。リクエストと応答の項目は契約（各リポジトリの `openapi/*.yaml`）にあるので書き写さない |
| エラー応答とテストの正 | エンドポイントごとの応答の条件は、各エンドポイントの文書を正とし、エラー応答の文書には、形と、どのエンドポイントにも共通の条件を書く。スモークテストで確かめることは [スモークテスト](shared/smoke-test.md) を正とし、各文書はスモークテストのまとまりの名前で指す |
| エラー応答の表に載せるもの | エラー応答の文書の表には、エンドポイント固有の条件を 1〜2 文の要約とリンクで載せてよい。`detail` の文言のような値は、正の文書（そのエンドポイントの文書。どのエンドポイントにも共通なら、エラー応答の文書）に書く |
| architecture との分担 | 細部（値、設定、理由）は設計の文書が持つ。[architecture](../architecture/README.md) は、全体の構成、流れ、用語、仮定と、設計の文書へのリンクを持つ |
| 仮定 | 仮定に頼る箇所に、[architecture の「仮定」](../architecture/README.md#仮定)の番号を 1 回書く（[docs の「書き方」](../README.md#書き方人が読める文書にする決まり)の W-10）。別の文書（同じフォルダでも、別のフォルダでも）に同じ番号があっても、その仮定に頼る文書の該当箇所に 1 回書く |
| 書かないもの | 決まっていないこと、作る順序、進み具合、後に回した課題、経緯、検討した案の比較。前の 4 つは issue に（[docs の「決まっていないことと作る順序は issue に書く」](../README.md#決まっていないことと作る順序は-issue-に書く)）、検討した案の比較は ADR に書く。全体像に「作業の進み具合は issue #N にある」と案内する 1 文は置いてよい（進み具合そのものは書かない） |

設計の文書にテンプレートはありません。新しく書くときは、同じフォルダの同じ種類の文書（例: エンドポイントの文書）を例にし、節の見出しを揃えます。

## 変更するときの流れ

変更は、集約リポジトリ（このリポジトリ fullstack-lab）の issue から始め、実装の前に、変わる部分の文書を変更後の作りに直します。issue は、[課題のテンプレート](../../.github/ISSUE_TEMPLATE/issue.md)で起票し、課題、決めること、やること（作る順序のチェックリスト）を書きます。順番と各段で行うことは、[docs の「書く順番」](../README.md#書く順番)にあります。

次の表は、その各段で AI に使わせるスキルとエージェント（評価だけを返すサブエージェント。[用語](../architecture/README.md#用語)）を示します。スキルは AI エージェント向けの手順書で、一覧は [AGENTS.md の表](../../AGENTS.md#設計の文書から実装する)にあります。

| 書く順番 | 段 | スキル・エージェント |
|---|---|---|
| 1 | ADR を書く（他の作るものにも従わせたい方針を決める変更のときだけ） | スキル `writing-docs` |
| 2 | 変わる部分の文書を直す・足す | スキル `writing-design-doc` |
| 3 | 文書を評価して直す | スキル `writing-docs`、エージェント `doc-review` |
| 4 | 決まった中身を文書に書いて評価し直し、issue の「やること」を作る | スキル `writing-design-doc`、`writing-docs` |
| 5 | 実装して PR を出す | スキル `implementing-from-design`、`pr-and-commit`。契約を変えるときは `updating-openapi-contract` |
| 6 | 文書と実装のずれを確かめる | スキル `implementing-from-design`、エージェント `design-review` |

| フォルダ | 全体像の文書 | 個別の文書の単位 |
|---|---|---|
