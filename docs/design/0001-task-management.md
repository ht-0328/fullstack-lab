## 解決する課題

この設計書は、タスクの一覧・登録・詳細表示と、期限日に関する外部サービス（カレンダー API）の補足情報を、どの構成要素がどう担うかを定める。このリポジトリは、業務環境（作成者が以前いた職場。このリポジトリはその構成を学習用に再現している。[用語](../architecture/README.md#用語)）に近い経路で業務フローを動かして学ぶためのもので、その最初の題材として一覧・登録・詳細を選んだ。リクエストは、画面から入口（すべてのリクエストを最初に受けて振り分けるもの。ローカルは Nginx、AWS では ALB）、BFF（画面専用のサーバー側 API）、API の順に流れ、API が DB と外部サービスを呼ぶ。この文書は実装済みの機能を記したもので、変更するときは実装より先にこの文書を直す。

次の表は、この題材の対象と規模、何ができれば完了かをまとめる。

| 項目 | 内容 |
|---|---|
| 対象 | タスクの一覧・登録・詳細表示と、期限日に関する外部サービスの補足情報 |
| 発生規模 | 学習用。利用者は数人、タスクは数百件以内 |
| 読者への影響 | 各技術の役割とリクエストの流れを、動くものを見ながら理解できる |
| 成功条件 | スモークテスト、Karate（API のテスト）、Playwright（画面のテスト）が通る。外部サービスが落ちていても詳細画面が表示される |

## 制約と前提

次の表は、この設計が従う制約と、成り立っているとして進める前提、学習用に置いた仮定を分けて示す。仮定の番号は [architecture/ の「仮定」](../architecture/README.md#仮定) の表の番号である。

| 区分 | 内容 | 根拠 |
|---|---|---|
| 制約 | ローカルは Docker Compose だけで完結する | 学習用で、AWS の費用をかけずに 1 台の PC で起動と再現ができることを優先するため。AWS 化は [ロードマップ](../roadmap/README.md) で段階的に進める |
| 制約 | 外部サービスは WireMock（HTTP のスタブサーバー）で代替し、スタブ（応答の定義）をリポジトリで管理する | 外部サービスの実体が無く、祝日・500・遅延の応答を再現してテストする必要があるため |
| 制約 | 領域（画面 + BFF、API、認可 API のように、独立したリポジトリで作る単位）同士はソースを共有せず、OpenAPI の契約でつなぐ | [0003 契約とリポジトリ分割](0003-contracts-and-repositories.md) |
| 前提 | 利用者の ID と表示名は、認証済みの BFF が JWT から得て API に渡す。JWT は、IdP（ログインを受け付けてトークンを発行するサービス。一般利用者は Keycloak、社員は Okta）が署名して発行するトークンである（[用語](../architecture/README.md#用語)） | [0002 認証と認可](0002-authentication-authorization.md) |
| 前提 | 期限日の補足情報は「あれば表示する」情報で、無くても業務は成り立つ | 題材の設定。外部サービスの障害で詳細まで見られなくならないようにするため |
| 仮定 | 外部サービスは、期限日が営業日か祝日かを返すカレンダー API とする | [構成の仮定 9](../architecture/README.md#仮定) |
| 仮定 | 社員はロールで、一般利用者は所有者かどうかで認可を判定する | [構成の仮定 5・6](../architecture/README.md#仮定) |
| 仮定 | API は BFF を信頼し、自分では認可しない | [構成の仮定 7](../architecture/README.md#仮定) |

## 採用案

画面専用の BFF と業務 API を別サービスにし、外部サービスとの連携は API に閉じる。業務環境でも、外部サービスとの連携は BFF ではなく API が担っていたためである（[業務環境について聞いている事実](../architecture/README.md#業務環境について聞いている事実)）。

次の表は、採用案を要素ごとに分け、採用した技術と責務を示す。

| 要素 | 採用内容 | 責務 |
|---|---|---|
| 画面 | Nuxt 4（初回はサーバーで HTML を作る SSR、以後はブラウザで画面を切り替える SPA） | 一覧・登録・詳細の表示。初回は SSR、その後はブラウザから同一オリジンの `/bff/*` を呼ぶ |
| BFF | Kotlin + Spring Boot | 認可 API への問い合わせ、API の結果を画面向けに集約、補足情報の縮退（取れないときは補足情報だけを諦め、詳細は返す） |
| 認可 API | Kotlin + Spring Boot | 「この主体はこの操作をしてよいか」の判定 |
| API | Kotlin + Spring Boot | 入力検証、永続化（表の作成と変更は、マイグレーションのツール Flyway で行う）、外部サービスの呼び出し |
| DB | PostgreSQL 17 | `tasks` 表 |
| 外部サービスの代替 | WireMock | 祝日・営業日・500・遅延のスタブ |

### 認可

次の表は、操作ごとに、利用者の種別別の可否を示す。社員はロールで、一般利用者は所有者かどうかで決まる。

| 操作 | 一般利用者 | 社員 `task-viewer` | 社員 `task-admin` |
|---|---|---|---|
| `task:list` | 自分のタスクだけ（`ownerId` で絞る） | 全件 | 全件 |
| `task:read` | 自分のタスクだけ。他人のものは 404 | 全件 | 全件 |
| `task:create` | 可 | 不可（403） | 可 |

### テスト

次の表は、層ごとに、どのテストで何を確かめているかを示す。対象の列に、テストのファイルを書いている。

| 層 | 対象 | 確かめること |
|---|---|---|
| 単体 | BFF の `TaskViewService`（`web/bff/src/test/kotlin/com/example/fullstacklab/bff/task/TaskViewServiceTest.kt`） | 一般利用者の一覧は自分のタスクだけに絞り、社員の一覧は絞らない。認可で拒否された登録は API を呼ばない。他人のタスクは 404 として隠す。認可 API が応答しないときは拒否する。詳細に補足情報を集約し、取れないときは `dueDateInfoStatus` を `UNAVAILABLE` にする。期限日が無いタスクでは補足情報を取りに行かない |
| Karate | API（`api/karate/features/tasks.feature`） | 登録したタスクを一覧と詳細で取得できる。所有者で絞った一覧に他人のタスクが含まれない。補足情報が外部サービスの応答（祝日、営業日、障害なら 502）で決まり、期限日が無ければ 404 になる。入力エラーは 400 の ProblemDetail（エラー応答の標準形式）、存在しない ID は 404 になる |
| Karate | 認可 API（`authz/karate/features/decisions.feature`） | 判定表の `task:list` / `task:read` / `task:create` が「認可」の表のとおりに許可・拒否になる。未知のロールやロールの無い社員は拒否になる |
| Playwright | 画面（`web/e2e/tests/tasks.spec.ts`） | 登録したタスクが詳細と一覧に出て、補足情報が表示される。外部サービスが落ちていても詳細は表示され、補足情報だけ縮退する。他の一般利用者のタスクは一覧に出ず、URL を直接開いても見つからない。`task-viewer` の社員は全件を閲覧できるが登録できず、`task-admin` の社員は登録できる |
| スモーク（集約） | 入口から DB と WireMock まで（`scripts/smoke-test.sh`） | 本人の一覧に出て、他の一般利用者の詳細は 404 になる。`task-viewer` の社員は全件を見られるが登録は 403 になる。詳細で補足情報を集約し、外部サービスの 500 と遅延では `UNAVAILABLE` になる。入力エラーの 400 が画面側まで返る。一覧と詳細が SSR で描画される |

## 比較した代替案とトレードオフ

次の表は、検討した案を採用案も含めて並べ、採否の理由を示す。

| 案 | 利点 | 欠点 | 採否の理由 |
|---|---|---|---|
| BFF を別サービスにする（採用） | 業務環境と同じ分担。画面が増えても再利用できる | サービスが 1 つ増える | 採用。業務環境と同じ分担を学ぶことが、このリポジトリの目的であるため |
| Nuxt のサーバールートを BFF にする | サービスが減り、TypeScript だけで書ける | Kotlin の知識が画面側で使えない。業務環境の分担（Nuxt と BFF が別の構成要素）と離れる | 不採用。小規模なら十分成り立つが、業務環境では Nuxt と BFF が別の構成要素で、BFF が認可 API を呼んでいた（[業務環境について聞いている事実](../architecture/README.md#業務環境について聞いている事実)）。その分担を学ぶ目的から外れる |
| API が画面向けの集約も担う（BFF なし） | 中継が減る | 画面の都合が業務 API に混ざる。認可の問い合わせ先が増える | 不採用。画面の都合が業務 API に混ざり、業務環境の分担（BFF が認可 API を呼ぶ）も再現できない |
| 補足情報を必須にする（取れなければ詳細もエラー） | 実装が単純 | 外部障害で詳細が見られない | 不採用。補足情報は「あれば表示する」情報という題材の前提（「制約と前提」の節）に反し、外部障害で詳細まで見られなくなるため |

## 失敗時の動作

次の表は、失敗の条件ごとに、どう検知し、システムがどう動き、利用者にどう見えるかを示す。認可 API の失敗は拒否（fail-closed）、外部サービスの失敗は縮退（補足情報だけを諦めて詳細は返す）にしている。

| 失敗条件 | 検知方法 | システムの動作 | 利用者への影響 |
|---|---|---|---|
| 外部サービスが 5xx を返す、または 3 秒以内に応答しない | API の `CalendarClient` が例外化し、`WARN` を記録 | API は 502（ProblemDetail）。BFF は `dueDateInfoStatus = UNAVAILABLE` で詳細を返す | 詳細は見られる。補足情報だけ「現在取得できません」 |
| 認可 API が応答しない | BFF の `AuthzClient` が例外化し、`ERROR` を記録 | BFF は 503。操作は許可しない（fail-closed） | 一覧・登録・詳細が使えない |
| API が応答しない | BFF の RestClient が例外化 | BFF は 502 | 一覧・登録・詳細が使えない |
| DB が落ちる | API のヘルスチェックが失敗 | API は再起動を繰り返す。復旧後に自動で戻る | 復旧まで使えない |
| 入力エラー | API の Bean Validation（項目に付けた注釈による入力検証） | 400（ProblemDetail）を BFF がそのまま返す | 画面に理由が出る |
