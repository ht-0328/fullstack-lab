# 契約のバージョンと変更の順序

この文書は、契約（領域同士の API の取り決め。各領域の `openapi/*.yaml`。[用語](../../architecture/README.md#用語)）のバージョンの決まりと、契約を変えるときに、どのリポジトリを、どの順で進めるかを記す。この文書では、契約を定義して公開する側を提供側、それを呼ぶ側を利用側と呼ぶ（[用語](../../architecture/README.md#用語)）。AI に作業させるときの手順は、スキル [updating-openapi-contract](../../../.agents/skills/updating-openapi-contract/SKILL.md) にある。

このフォルダの全体と、文書で使う語の意味は [領域をまたぐ仕組みの全体像](README.md) にある。

## バージョンの決まり

次の表は、バージョンを書く場所を示す。提供側の 2 つの値は、同じ値に、同時に上げる。

| 場所 | 中身 |
|---|---|
| 契約の `info.version` | 契約のバージョン |
| 提供側のリポジトリの `gradle.properties` の `version` | publish（Maven リポジトリに登録すること。[用語](../../architecture/README.md#用語)）するクライアントのバージョン。契約の `info.version` と同じ値にする |
| `web/bff/gradle.properties` の `apiClientVersion`、`authzClientVersion`、`authClientVersion` | BFF が使うクライアントのバージョン |

次の表は、変更の種類ごとに、互換性と上げるバージョンを示す。

| 変更 | 互換性 | 上げるバージョン |
|---|---|---|
| エンドポイントや項目の追加 | 互換 | パッチバージョンかマイナーバージョン |
| 必須の項目の追加、項目の削除、型の変更 | 非互換 | メジャーバージョン |

古いバージョンのクライアントは Maven リポジトリに残る。そのため、提供側と利用側を同時にデプロイしなくてよく、利用側は自分のタイミングで新しいバージョンに追従する。利用側が古いバージョンのままでも、検知はしない。古い契約で動き続け、新しい項目が使えないだけである。

## 変更の順序

契約を変えるときは、提供側、利用側、集約リポジトリの順に進める。利用側の CI が、提供側の publish したクライアントを取得するためで、逆にすると利用側のビルドが依存を解決できない。

流れは [全体像の「契約を変えてから利用側が取り込むまで」](README.md#契約を変えてから利用側が取り込むまで) の図にある。次の表は、各段で書き換えるものを示す。

| 段 | リポジトリ | 書き換えるもの |
|---|---|---|
| 提供側 | `api`、`authz`、`auth` | 契約の `info.version` と `gradle.properties` の `version`、生成コード、実装 |
| 利用側 | `web` | `web/bff/gradle.properties` のクライアントのバージョン、実装 |
| 集約リポジトリ | fullstack-lab | サブモジュールの参照 |

BFF の契約 `web/openapi/bff.yaml` だけを変えるときは、提供側も利用側も `web` リポジトリの中にあるので、1 つの PR で進める。生成のしかたは [契約からのコード生成](code-generation.md) に、publish の仕組みは [生成クライアントの publish と取得](client-distribution.md) にある。

## 元に戻す方法

利用側を前の契約に戻すときは、開発者が `web/bff/gradle.properties` のクライアントのバージョンを前の値に戻す。古い成果物は残っているので、取得できる。
