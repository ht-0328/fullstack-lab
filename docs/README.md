docs/ は、開発者と AI エージェントが読む文書の置き場です。この README は、文書の種類ごとの置き場所と役割（docs/ に書かない進み具合と作業の報告を、issue と PR のどちらに置くかを含む）、書く順番、人が読める文書にする書き方と形式の決まり、判定に迷うときの扱いを説明します。文書は AI エージェントとの会話の中で書くことが多いので、会話に居なかった人が読み進められることを決まりにしています。決まりどおりかは、評価エージェント [doc-review](../.claude/agents/doc-review.md)（文書を読み、決まりとのずれの指摘だけを返すサブエージェント）で確かめます。

人向けの図解（HTML）は、別リポジトリの [fullstack-lab-architecture-notes](../references/architecture-notes/README.md) にあり、ここの文書を元に描き直したものです。食い違ったら、ここの文書に合わせて図解を直します。

## 種類と置き場所

次の表は、文書の種類ごとに、どの問いに答える文書をどのフォルダに置き、どう更新するかを示します。新しく文書を書くときは、まずどの行に当たるかを決めます。

| [architecture/](architecture/README.md) | 今どうなっているか | 構成図、各サービスの役割、リクエストの流れ、用語、業務環境（作成者が以前いた職場。このリポジトリはその構成を学習用に再現している）について分かっている事実と、学習用に置いた仮定（[architecture/ の「仮定」](architecture/README.md#仮定)） | 常に最新にする。変更の実装がマージされたら、その内容をここに反映する |

文書の種類は、この表のものだけです。人が環境を操作するための運用手順書（起動、デプロイ、環境の削除）が要るようになったら、この表に種類を足します。

作業の進み具合と作業の報告（何をどう変え、どう確かめたか）は、docs/ に書かず GitHub に置きます。設計の文書と ADR は決めたこと（何をどう作るか、どの方針にしたか）を書く文書なので、進み具合や作業の報告を混ぜると、作業が進むたびに書き換えが要り、すぐに古くなるためです。次の表は、GitHub の 2 つの置き場所（issue と PR）に、それぞれ何を置くかを示します。issue には、進み具合のほかに、変更の出発点になる課題（困っていること、決まっていないこと、残った作業）と、作る順序も置きます。

| 置き場所 | 答える問い | 置くもの |
|---|---|---|
| 集約リポジトリ（このリポジトリ fullstack-lab。[用語](architecture/README.md#用語)）の issue | 何が困っていて、何が決まっておらず、作業がどこまで進み、何が残っているか | 困っていること、決まっていないこと、PR や評価で残った作業が見つかったら、課題 1 つにつき 1 つ、[課題のテンプレート](../.github/ISSUE_TEMPLATE/issue.md) で起票する。同じ課題の issue が既にあればコメントを足し、途中で詰まったことや分かったこともコメントに書く。issue の各節の書き方（「決めること」と、「やること」のチェックと PR へのリンク）は「書く順番」の節にある。作業が複数のリポジトリにまたがっても、進み具合を 1 か所で追えるように、issue は集約リポジトリにだけ起票する |
| PR | 何をどう変え、どう確かめたか | 各リポジトリの `.github/pull_request_template.md`（例: 集約リポジトリの [PR のテンプレート](../.github/pull_request_template.md)）に沿った本文。その PR が取り組む課題の issue へ `Refs ht-0328/fullstack-lab#番号` でリンクする。サブモジュール（集約リポジトリが git submodule で参照するリポジトリ。PR のテンプレートを持つのは web、api、authz、auth、infra）の PR からも集約リポジトリの issue を指すため、リポジトリ名から書く。`Closes` はマージで issue が閉じるので使わない |

## 設計の文書と ADR の使い分け

設計の文書と ADR はどちらも「決めたこと」を書くので、迷いやすい組み合わせです。主語が「作るもの」なら設計の文書、「方針」なら ADR と覚えます。

- 設計の文書は「作るもの」が主語です。エンドポイントの処理と応答、設定、失敗時の動作、テストのように、作るものと作り方を書き、実装の入力にします。その作りにする理由は、該当する行か段落に書けば足ります。検討した案の比較と、作るものに関係の無いこと（業務環境の経緯、学習の目的、文書自身の説明）は書きません
- ADR は「方針」が主語です。1 つの作るものに収まらず、将来の変更にも効くルールと理由だけを短く書きます。検討した他の案と、採らなかった理由も ADR に書きます。例: [ADR-0003 生成コードは git で管理する](adr/ADR-0003-commit-generated-code.md)
- 迷ったら「この決定に、他の作るものも従わせたいか」で決めます。従わせたいなら ADR を書き、設計の文書からリンクします
- 例: 手元（開発者が作業する PC。[用語](architecture/README.md#用語)）から AWS を操作する道具をコンテナで動かすという方針は [ADR-0005](adr/ADR-0005-infra-tools-container.md) に書き、そのコンテナの作りは設計の文書 [道具のコンテナ](design/infra/tools-container.md) に書きました。タスクの完了を冪等（同じ操作を何度行っても結果が変わらないこと）にする判断は、設計の文書 [タスクの完了](design/api/task-completion.md) の中だけに書き、ADR にはしていません

## 決まっていないことと作る順序は issue に書く

決まっていないこと、作る順序（1 件の変更を進めるための PR の分け方と作業の段取り）、後に回した課題は、設計の文書に書かず、その変更の issue に書きます。設計の文書は今の作りを書く文書で、決まるたび、作業が進むたびに書き換えが要る内容を混ぜると、すぐに古くなるためです。決まっていないことは issue の「決めること」に、作る順序は「やること」のチェックリストに書きます。決まった中身は、設計の文書の本文に書きます。

## 書く順番

1 件の変更について、文書を直してから実装に反映するまでの順番です。変更は、集約リポジトリの issue（課題を起票したもの。「種類と置き場所」の節）から始めます。その変更の issue がまだ無ければ、最初に起票します。

1. 他の作るものにも従わせたい方針を決める変更なら、ADR を書く（[ADR のテンプレート](adr/TEMPLATE.md)）。[ADR の索引](adr/README.md) に 1 行足す
2. 変わる部分の設計の文書を、変更後の作りに直す。新しく作るものは文書を 1 本足し、そのフォルダの全体像の `README.md` に 1 行足す（[design/ の「文書の単位と書き方」](design/README.md#文書の単位と書き方)）。決まっていないことは文書に書かず、issue の「決めること」に書いて、決める人（作成者。AI が書くときは、指示した人）に質問する
3. 直した文書を `doc-review` エージェントで評価して指摘を直し、止める条件（[review/ の「止める条件」](review/README.md#止める条件)）を満たすまで繰り返す。手順はスキル（AI エージェント向けの手順書）[writing-docs](../.agents/skills/writing-docs/SKILL.md) にある。結果は [review/](review/README.md) に残す
4. issue の「決めること」が無くなったら、決まった中身を文書の本文に書き、書き足した部分を 3 の手順でもう一度評価する。issue の「やること」を作る順序のチェックリストにする。「決めること」が残っているうちは実装を始めない
5. issue の「やること」の順に実装し、PR を出す。段が済むたびに、issue の「やること」にチェックを付け、その段の PR へリンクする。文書と違う判断が要ったら、黙って実装を変えず、文書を直して差分を PR に書く
6. 最後の段の PR をマージしたら、`design-review` エージェントで文書と実装のずれを確かめ、結果を [review/](review/README.md) に残す。後に回した作業や、直さなかったずれが残ったら、新しい issue を起票する。[architecture/](architecture/README.md) と [roadmap/](roadmap/README.md) を今の状態に合わせ、issue を閉じる

AI に任せるときのスキルとエージェントの一覧は [AGENTS.md の「設計の文書から実装する」](../AGENTS.md#設計の文書から実装する) の表にあります。

## 書き方（人が読める文書にする決まり）

文書の読者は、その文書を書いたときの会話に居なかった人です。新しくチームに入った人が、他の文書を開かずに読み進められることを目標にします。次の表の決まりは番号で呼び、`doc-review` エージェントはこの番号で指摘します。

| 番号 | 決まり | 良い例と悪い例 |
|---|---|---|
| W-1 導入 | 先頭の表（表を置かない文書では題名）の次の段落で、「何の文書か」と「何を決める（説明する）か」を 2〜4 文で言う。ADR は「なぜ今か」も言い、設計の文書、索引、README、architecture、roadmap は「何の文書か」「何を載せているか」で足りる。「誰のために」は先頭の表の想定読者で足り、本文で繰り返さなくてよい。本文を表や箇条書きから始めない（先頭の表は除く） | 悪: 「業務環境では、画面と BFF の間も OpenAPI から型を生成していたが、クライアントは自前で書いていた。相性が悪いのかという疑問があった。」 良: 「画面（Nuxt）が BFF を呼ぶコードを、OpenAPI の契約からどこまで生成するかを決める。このリポジトリは作成者が以前いた職場の構成を再現しており、その職場では型は生成し、クライアントは手で書いていた。」 |
| W-2 前提と用語 | 読者が役割を知らないと文が読めない語は、文書の中での初出に一言そえる。対象は、リポジトリ固有の前提（例: 業務環境、集約リポジトリ、領域、契約、入口、前段）、概念語（例: JWT、BFF、SSR、IdP、冪等、publish）、製品名・ツール名（例: Keycloak、ALB、Karate、Flyway）で、コードの識別子（例: 関数名、クレーム名）は何をするか分からないと文が読めないときだけにする。[architecture/ の「用語」](architecture/README.md#用語) にある語は、初出でその表へリンクすれば一言に代えてよい。他の文書の題名を引用した部分は対象外 | 良: 「業務環境（作成者が以前いた職場。このリポジトリはその構成を学習用に再現している。[用語](architecture/README.md#用語)）」「Karate（API のテスト）」 |
| W-3 表のリード | 表、箇条書き、図、抜粋の前に、それが何を示しどう読むかを 1〜2 文置く。節を表だけで構成しない。表の後の文は、結論や注意があるときだけ書く。先頭の表、各項目が結論の文で始まる箇条書き、見出しが中身を言い切っている 1 行の表は除く | 良: 「次の表は、利用者の種別ごとに完了操作の可否を示す。社員はロールで、一般利用者は所有者かどうかで決まる。」 |
| W-4 理由 | 判断、採否、数値には理由を添える。理由が同じ文書の別の節にあるなら、その節名で参照すればよい。設定値は出所（どのファイルの値か）を書けば理由に代えてよい。表のセルは、意味が取れる名詞句なら体言止めでよいが、理由・判断・手順のセルは文にする | 悪: 「候補 \| typescript-fetch、openapi-fetch」 良: 「候補は 2 つ。typescript-fetch は HTTP の層まで生成し、openapi-fetch は型だけを生成する。」 |
| W-5 経緯と進み具合を書かない | 会話で出た疑問や指示をそのまま書かず、「〜という疑問があった」「〜と言われた」は何が分からず何を決める必要があったかに、「選んでもらう」「確認を取る」は誰が何を決めるか（例: 「作成者が決める」「作成者が承認してから始める」）に直す。作業の報告（何をどう変え、どう確かめたか。誰がいつ行ったかも含む）と進み具合（どこまで済んだか。ADR の状態の行（F-2）は除く）は書かずに issue と PR に置き（「種類と置き場所」の節）、今の環境の状態（何があり、どう設定されているか）は [architecture/](architecture/README.md) に書く。日付は先頭の表（発信日、最終確認日）と、ADR の「適用開始日」「適用対象」「対象外」の行にだけ書く。評価の記録と roadmap/ のフェーズの状態の扱いは「判定に迷うときの扱い」の節にある | 悪: 「Nuxt と OpenAPI の相性が悪いのかという疑問があった。」「AWS のアカウントは 2026-11-03 に作成者が用意し、MFA と予算アラートまで設定した。」 良: 「生成できるはずの部分をなぜ手で書いていたのかが分からず、Nuxt では生成したクライアントが使いにくいのかを確かめる必要があった。」「AWS のアカウントは 1 つで、root ユーザーに MFA、月 10 ドルの予算アラートが付いている。」（この内容は architecture/ に書く） |
| W-6 文の形 | 1 段落は 4 文まで（短い段落は可）とし、表のセルも 1 段落として数える。1 文に 1 つのことを、主語を省かず「誰が、何を、どうする」の順に書く（手順の箇条書きと、方針を言い切る文（ADR の決定）は主語を省いてよい）。矢印（→）や記号の羅列を文の代わりにせず、経路や順序は「A → B → C の順に流れる」のように文の中で使う。文の数え方（括弧の中を含む）は「判定に迷うときの扱い」の節にある | 悪: 「取得は匿名。」「状態: 採用 → 廃止。」 良: 「BFF は Reposilite から匿名でクライアントを取得する。」「状態は「採用」から始まり、新しい ADR で置き換えたら「廃止」に進む。」 |
| W-7 具体 | 値、ファイル名、URL、コマンド、画面の文言を具体的に書く。「適切に」「必要に応じて」で済ませない。「下記」「後述」「上の表」ではなく節名で指す。他の節や他の文書と食い違う記述（数、名前、一覧の抜け）を残さない | 良: 「`authz/src/main/resources/application.yml` の `task-admin` に `task:complete` を足す」 |
| W-8 見出しで追える | 見出しを読むだけで構成が分かる。節の中身が見出しと一致し、1 つの節に 2 つの話を入れない。同じ見出しを 2 回使わない | 悪: 設計の文書の処理を書いた節に、検討した案の比較が混ざる（比較は ADR に書く）。「設計上のポイント」が 2 か所にある |
| W-9 言葉の統一 | 同じものは同じ言葉で呼び、[architecture/ の「用語」](architecture/README.md#用語) に合わせる。一般名と具体名を両方使うときは、初出で「外部サービス（カレンダー API）」のように結び、以後は一般名で呼ぶ。同じ手順や事実を 2 つの文書に書かず、片方へリンクする。全体の流れを書く文書（docs/README.md など）は、詳細を書く文書の節へリンクし、詳細を書き写さない | 悪: 同じ文書の中で「入口」「ゲートウェイ」「Nginx」が同じものを指す。「利用者」がアプリの利用者と文書の作成者の両方を指す |
| W-10 事実と仮定 | 業務環境の事実と学習用の仮定を分け、仮定を事実のように書かない。仮定は、設計の文書ではその仮定に頼る箇所に、ADR では「状況」の表に 1 回書いて [architecture/ の「仮定」](architecture/README.md#仮定) の番号を付け、本文で触れるたびには番号を付けなくてよい。その文書だけの仮定で architecture の表に無いものは「構成の仮定には載せない」と書く。業務環境と無関係の未決の選択は「仮定」と呼ばず「未決」か「前提」と書く | 良: 「認証 API の責務は不明なので、Keycloak のユーザー管理の代行と仮定する（仮定 12）」 |

この決まりは、評価の記録（[review/](review/README.md)）で同じ指摘が繰り返されたら見直します。判定に迷った点の扱いと、決まりが曖昧で判定できない指摘の扱いは、「判定に迷うときの扱い」の節にあります。

## 形式の決まり

次の表は、書き方の決まりとは別の、形式の決まりです。docs/ のすべての文書に当てはめ、`doc-review` はこの番号でも指摘します。

| 番号 | 決まり |
|---|---|
| F-1 日本語 | 日本語で書く。技術用語は英語のままで構わない |
| F-2 先頭の表と状態 | 各文書の先頭に、この文書と同じ表（発信日、作成者、機密区分、保守責任者、最終確認日、想定読者、読んだあとできること）を置く（設計の文書には置かない。評価の記録 `review/docs-*.md` は、この表の代わりに [review/ の「記録の形」](review/README.md#記録の形) の表を使う）。ADR は、題名の次に `> **状態: 〜。**` の行を置き、状態と置き換えの関係（例: 「廃止（ADR-NNNN で置き換え）」）だけを書いて、日付と理由は書かない（W-5）。ADR を廃止した理由は、置き換える側の新しい ADR の「状況」に書く。最終確認日は、事実を確かめ直したときと、決まりや運用を書いた文書でその決まりや運用を変えたときに更新し、読みやすさだけの修正では変えない（「判定に迷うときの扱い」の節） |
| F-3 文書の構成 | ADR はテンプレートの節と表の行を揃え、空欄のまま残さない。該当しない節は本文に理由を 1 文書き、該当しない行は、行を残してセルに理由を書くか、行を削って同じ節の本文に理由を 1 文書く。表の列名は影響を受ける相手に合わせて変えてよく（例: 配布の失敗は「開発者への影響」）、ADR の「結果と影響」の「影響する対象」には影響を受ける人（例: 画面の開発者、PR のレビュアー）を書く。設計の文書は、[design/ の「文書の単位と書き方」](design/README.md#文書の単位と書き方) に従う（題名は作るものの名前、1 本に作るもの 1 つ） |
| F-4 コードを書かない | 実装と二重になり古くなるので、文書にコードは書かない。契約の差分は OpenAPI の抜粋、設定の差分は設定ファイルの抜粋、記録の形は Markdown の抜粋で示してよい。図（mermaid）は書いてよい |
| F-5 リンク | 他の文書とは相対リンクでつなぎ、ファイルを動かしたらリンクも直す。文書（スキルとエージェントの定義を含む）を名前で参照するときはリンクにし、表示文言はパスではなく文書名や見出し名にする（フォルダへのリンクは、フォルダ名（`review/` など）を表示文言にしてよい）。設計の文書は、従う ADR へリンクし、どの文書も少なくとも [architecture/](architecture/README.md) か索引へ 1 つはリンクする |
| F-6 設計の文書に書かないもの | 設計の文書に、決まっていないこと、作る順序、進み具合、後に回した課題を書かない。これらは issue に書く（「決まっていないことと作る順序は issue に書く」の節） |

## 判定に迷うときの扱い

次の表は、書き方と形式の決まりのうち、評価で判定が揺れた点の扱いを決まりの番号ごとに示します。`doc-review` は、この表も決まりの一部として使い、この表と「書き方」「形式の決まり」の表が違う答えを出すように見えるときは、この表の行を優先します。ここに無い迷いは、`doc-review` が「決まり側の課題」として返し、文書を書いた人が評価の記録にためて、スキル [writing-docs](../.agents/skills/writing-docs/SKILL.md) の手順で決まりに反映するか issue に起票します。

| 決まり | 迷う点 | 扱い |
|---|---|---|
| W-1 | 導入 | 1 段落目で「何の文書か」と「何を決める（説明する）か」を言えば足り、「なぜ今か」は 2 段落目でよい。導入で「この文書は A、B、C を説明する」と並べるときは、主な節だけを挙げればよく、「例:」「主なもの」「など」は書かなくてよい |
| W-2 | 一言が要らない語 | 次の語は、このリポジトリで作業する人が既に知っているものなので、一言をそえなくてよい。開発の前提の道具と形式（Docker、Docker Compose、git、GitHub、GitHub Actions、WSL、AWS、Claude Code、Markdown、HTML、YAML、mermaid、OpenAPI）と、その基本の機能（GitHub の issue と PR、git のブランチと submodule）。プログラミング言語と実行環境（Kotlin、Java、TypeScript、JDK、Node.js、npm）と CI。名前だけで役割が読み取れる機能名（管理コンソール、アカウントコンソール） |
| W-2 | 一言が要る語 | 「一言が要らない語」の行に無い製品名・ツール名（例: Maven、Gradle、Nuxt、Keycloak）、製品の機能名（例: ALB のリスナールール、Keycloak の `realm-management`、GitHub Packages）、略語（例: PDP）には、役割を一言そえる。生成方式の名前（例: `kotlin-spring`）のような設定値は、コードの識別子と同じく、何をするか分からないと文が読めないときだけ一言そえる |
| W-2 | 初出に数える場所 | 本文（段落、箇条書き、本文の表）での最初の出現を初出とする。先頭の表、状態の行、図（mermaid）の中、一言の中の語と、この文書と [design/ の README](design/README.md) の決まりの表で例として挙げた語（「例:」「良:」「悪:」の後と、括弧の中、「など」や「のような」の前に挙げた例）は数えない。初出が表のセルなら、表のリードで前出しするか、セルの中で括弧書きにする |
| W-2 | 設計の文書の一言 | 設計の文書では、用語の表にある語と、フォルダの全体像で一言をそえた語は、個別の文書で繰り返さなくてよい。範囲は [design/ の「文書の単位と書き方」](design/README.md#文書の単位と書き方) の「語の一言」「語の表」の行にある |
| W-2 | 一言の書き方と、一言の代わり | 一言には読者が分かる語だけを使い、一言の中の語にさらに一言はそえない。括弧が 3 重になるときは、その語を表のリードか前の文で先に説明する。一言の代わりになるのは、初出の位置にある [architecture/ の「用語」](architecture/README.md#用語) へのリンクだけで、ほかの節へのリンク、段落の末尾にまとめたリンク、「入口の Nginx」のような具体名との併記は代わりにならない |
| W-3 | リード | リードは、表全体が何を示すかを 1〜2 文で言えばよく、列を説明するときも 4 文まで。関連する文書へのリンクだけを並べた箇条書きには、リードは要らない |
| W-4 | 測った値と計算した値 | 測った値は、測った条件を環境と対象で書き（例: WSL の Docker で、`api` の `check-generated` ステージだけを作り直した）、日付と測った人は書かない（W-5）。計算した値は、計算の元（どの行を足したか）を書く。どちらも、書けば理由に代えてよい |
| W-4 | 理由が要る範囲 | 索引や README の運用の決まりにも理由を書く。ただし、この文書の決まりの表（書き方、形式、この節）の各行には理由を求めない（決まりを変えた理由は評価の記録と issue に残る）。ADR の中の数値や細かい判断は、理由を書いた設計の文書へリンクすれば理由に代えてよいが、決定そのものの理由は ADR の「理由」の節に書く |
| W-5 | 書いてよいもの | 評価の記録（review/）は記録そのものなので対象外。roadmap/ のフェーズごとの状態（未着手、進行中、完了）は計画の一部なので書いてよく、フェーズの中の作業の進み具合は issue に置く。設計の文書と ADR の「状況」には、決定の前提になる環境の事実（例: 作成者の環境は WSL）を書いてよいが、日付と誰が用意したかは書かず、architecture/ に同じ事実があればその節へリンクする |
| W-5 | 引用の中の日付 | 画面の文言やテストのデータを引用した中の日付は、日付の決まりの対象外 |
| W-5 | 環境の今の状態と、時点で変わる値 | architecture/ に書く環境の今の状態は「何があるか」で書き、「まだ〜していない」のように予定に触れない。価格のように時点で変わる値（roadmap/ の費用など）は「最終確認日の時点」と書き、先頭の表の日付を指す |
| W-6 | 表のセルが 4 文に収まらない、文の数え方 | 収まらない分は、同じ節の中の小見出し（`###`）か、既にある別の節に書き、セルからその見出しの名前で指す。関係の無いことを 1 文につながない。文の数は、`scripts/doc-lint.py`（docs/ の文書の形式を機械で確かめるスクリプト）と同じく、括弧の外で数える。括弧の中は 2 文までにし、それより長いときは括弧の外の文にする |
| W-7 | 一覧と数 | 一覧の一部だけを挙げるときは「例:」「主なもの」「など」のどれかを書く（導入は W-1 の行のとおり）。表のリードで範囲を言った表は、その範囲のものをすべて載せる。リポジトリ、サービス、契約、エージェント、AWS のリソースなど作るものの数は、名前をすべて並べた直前か直後（すぐ後の表や抜粋を含む）に添えるときだけ書く（例: 「`api`、`authz`、`web` の 3 つ」）。数だけを書くと増減で食い違うためで、人数、件数、文書の本数のような数は書いてよい |
| W-7 | パスの書き方 | 集約リポジトリの文書では、サブモジュールの中のパスを集約リポジトリから見たパス（`infra/bootstrap`）で書く。領域（[用語](architecture/README.md#用語)）ごとに同じ形のパスは「各領域の `openapi/*.yaml`」のように、どのリポジトリの中のパスかを添える。サブモジュールの README では、そのリポジトリから見たパスで書く |
| W-7 | 食い違いを見る相手 | docs/ の文書、この文書（決まり）、テンプレート、スキルとの食い違いを見る。ただし、テンプレートの例と例を取った文書の食い違い（F-3 の「テンプレート」の行）と、採用したあとの ADR と廃止した ADR がリンク先と食い違うこと（F-3 の「採用したあとの ADR」の行）は直さない |
| W-9 | 用語の表の言い換えが及ぶ範囲 | 「本文では〜と書く」は、表の行名とリードを含む文書の全体に及ぶ。データベースのマイグレーションの番号も「バージョン」と書く（用語の表の「バージョン」の意味に含める） |
| W-9 | 一般語と、1 つの語の 2 つの用途 | 一般語が 2 つのものを指しうるときは、毎回修飾する（「ECR のリポジトリ」）。1 つの語を 2 つの用途で使うとき（例: OIDC を、ALB の認証と GitHub Actions の認証の両方に使う）は、用語の表へのリンクだけでなく、それぞれの初出で用途を言う |
| W-9 | 要約と書き写しの境目 | 別の文書に詳細がある事実は、1〜2 文の結論（固有名を含めてよい。例: グループ名、ポリシー名）とリンクだけを書き、理由や手順は書き写さない。これから書き足す先の指示（「動いたら A に書き足す」）は書き写しに当たらない |
| W-9 | 設計の文書どうし、architecture との重なり | エラー応答の文書と各エンドポイントの文書、スモークテストと各文書、architecture と設計の文書のどちらを正にするかは、[design/ の「文書の単位と書き方」](design/README.md#文書の単位と書き方) の「エラー応答とテストの正」「エラー応答の表に載せるもの」「architecture との分担」の行にある。図と文の重なりは F-3 で指摘する |
| W-9 | 呼び分け | アプリを使う人は「利用者」、Keycloak（一般利用者と社員のログインを受け付ける製品）に登録されたアカウントは「Keycloak のユーザー」と書く。成果物を登録して配布するサービスの一般名は「成果物リポジトリ」、Maven 形式（Java と Kotlin のライブラリを配布する形式）のものは「Maven リポジトリ」と書き、「パッケージリポジトリ」とは書かない。表の行名や列の「集約」は、集約リポジトリの略称としてそのまま使ってよい |
| W-10 | 仮定と、確かめていない主張 | 仮定は文書ごとに 1 回書く。公開の記事にあるだけで公式の文書で確かめていない技術的な主張は、出所へリンクし、「公式の文書では確かめていない」と、どの作業のときに確かめるか（日付ではなく作業で書く。例: フェーズ 4 の着手前）を書く。設計の文書では、出所へリンクして「公式の文書には記載が無い」と書くにとどめ、確かめる作業は issue に書く（F-6） |
| F-2 | 先頭の表を置かない文書 | 設計の文書（`design/web/` など、設計の文書のフォルダの文書）には、全体像の `README.md` も含めて先頭の表を置かず、題名の次を導入の段落にする。文書が短く、表の値がどの文書でも同じになるためで、書いた人と日付は git の履歴で分かる |
| F-2 | 最終確認日 | 文書の事実の一部でも、コード、設定、他の文書やスキルと照らして確かめ直したら更新する。決まりや運用を書いた文書（この文書、[review/](review/README.md)、索引）は、その文書に書いた決まりや運用を変えたときにも更新し、読みやすさだけの修正では変えない。確かめ直したかどうかは書いた人が決め、`doc-review` は、本文の事実と最終確認日の食い違いが文書から読み取れるときだけ指摘する。価格のように時点で変わる値（roadmap/ の費用など）を載せた文書は、最終確認日を更新するときにその値も確かめ直す |
| F-3 | 節と行と列 | テンプレートの節は分けず、分けたいときは節の中に小見出し（`###`）を置く。表の行名は括弧書きを省くほかは変えず、テンプレートに無い行は、表の最後に限って足してよく、行は行名の問いに答えていれば中身がテンプレートの括弧書きと違ってもよい。列は削らず、2 つの列を 1 つにまとめるときは列名に両方の名前を書き（例: 「変更 / 変えない理由」）、列名は相手に合わせて変えてよい。該当しないセルには理由を書くが、同じ行の別の列で答えが分かるセルは「—」でよい |
| F-3 | テンプレート | テンプレートの「書くこと」と例は書き方の手引きで、決まりそのものは、W と F の番号、この節の表、[design/ の「文書の単位と書き方」](design/README.md#文書の単位と書き方) の表で書いたものだけ。テンプレートの例は、例を取った文書が後で直っても揃えなくてよく、節の冒頭の文は実際の書き方に合わせて直してよい。テンプレートが変わったら、既存の文書は次に直すとき（読みやすさの修正を含む）に、直した節だけでなく文書全体を新しい形に揃える。評価の記録の形を変えたときの扱いは [review/ の「記録の形」](review/README.md#記録の形) に従う |
| F-3 | 設計の文書の構成 | 設計の文書にはテンプレートが無い。[design/ の「文書の単位と書き方」](design/README.md#文書の単位と書き方) の表の行（題名、言い回し、言い回しの及ぶ範囲、見出しの揃え方、確かめる方法の節、1 本に 1 つ、全体像の文書、文書の一覧、流れの図、全体像の図に描く範囲、図と本文、図と重なる文、図と文や表の両方があってよい場合）のどれかに反していれば F-3 で指摘する |
| F-3 | 索引 | 索引にはテンプレートが無いので、[ADR の索引](adr/README.md) は、導入、流れ（あれば）、索引の表のリード、索引の表、状態の説明の順に置く。[design/ の README](design/README.md) は、導入、文書の単位と書き方、変更するときの流れ、フォルダごとの全体像、関連の順に置く。状態の列は「採用」「廃止」などの状態の語だけでよい |
| F-3 | 採用したあとの ADR | 適用対象が増えたら、「適用対象」か「対象外」に追加分と当てはめ始めた日を書き、「状況」の末尾に「〜（設計の文書へのリンク）にも、この決定を当てはめる。」の形の注記を 1 文足す。決定が仮定に頼ると分かったら、「状況」の表の仮定の行（削っていれば表に足す）に番号を書き、「結果と影響」に「仮定 N が崩れたら見直す」を足す。この 2 つの追記と、読みやすさの修正、テンプレートの新しい形に揃える修正（F-3 の「テンプレート」の行）、リンク切れの修正（F-5）のほかは、既にある文を書き直さない（前の方式を覆した ADR は、リンク先の設計の文書が後で直っても書き直さない）。廃止した ADR は、この 2 つの追記もせず、リンク先が後で変わった食い違いも直さない |
| F-3 | ADR の「影響する対象」 | 人で書く。「提供側」のような立場は「提供側のリポジトリの開発者」のように人に直す |
| F-4 | 契約の抜粋 | 設計の文書には、リクエストと応答の項目を契約から書き写さず、契約へリンクする。設定の抜粋は、その文書が説明する部分だけでよい |
| F-5 | リンクの回数と相手 | 同じ文書を名前で指すときは、文書の中での初出をリンクにすれば足りる。表のセルにバッククォートで書いたスキルとエージェントの名前は、表のリードで [AGENTS.md の表](../AGENTS.md#設計の文書から実装する) へリンクすれば足りる。設計の文書から廃止した ADR へはリンクせず、置き換えた ADR へリンクする |
| F-5 | 設計の文書のリンク | 設計の文書は、導入で全体像（そのフォルダの `README.md`）へリンクすれば、「architecture か索引へ 1 つ」を満たす |
| F-5 | 表示文言 | 表示文言は、見出し名を意味が変わらない範囲で縮めてよく、見出し名の前にリンク先の文書の呼び名を、後に表の行の番号を添えてもよい（例: 「構成の仮定」「仮定 11」）。本文の語にそのままリンクを付けてもよい。ファイルをパスで示す表のセル（例: [review/ の「合格までの回数の実績」](review/README.md#合格までの回数の実績) の「文書」の列、評価の記録の先頭の表の「対象」の行）ではパスでよい |
| F-6 | 作る順序と進み具合の範囲 | 「作る順序」が指すのは、1 件の変更を進めるための PR の分け方と作業の段取り（issue の「やること」に書くもの）である。仕組みを作る、変えるたびに同じになる順序（人が行う操作を含んでよい）と、全体像に置く issue への案内の 1 文は当たらない。範囲は [design/ の「文書の単位と書き方」](design/README.md#文書の単位と書き方) の「仕組みの作りとしての順序」「書かないもの」の行にある |
