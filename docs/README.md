docs/ は、開発者と AI エージェントが読む文書の置き場です。この README は、文書の種類ごとの置き場所と役割、書く順番、人が読める文書にする決まりを説明します。文書は AI エージェントとの会話の中で書くことが多いので、会話に居なかった人が読み進められることを決まりにし、評価エージェント `doc-review`（文書を読んで決まりとのずれを指摘だけ返すサブエージェント）で確かめます。人向けの図解（HTML）は別リポジトリ [references/architecture-notes](../references/architecture-notes/README.md) にあり、ここの文書を元に描き直したものです。食い違ったら、ここの文書に合わせて図解を直します。

## 種類と置き場所

次の表は、文書の種類ごとに、どの問いに答える文書をどのフォルダに置き、どう更新するかを示します。新しく文書を書くときは、まずどの行に当たるかを決めます。

| フォルダ | 答える問い | 置くもの | 更新のされ方 |
|---|---|---|---|
| [architecture/](architecture/README.md) | 今どうなっているか | 構成図、各サービスの役割、リクエストの流れ、用語、業務環境（作者が以前いた職場。このリポジトリはその構成を学習用に再現している）について分かっている事実と、学習用に置いた仮定（[architecture/ の「仮定」](architecture/README.md#仮定)） | 常に最新にする。設計書が実装済みになったら、その内容をここに反映する |
| [design/](design/README.md) | この変更を、何を、どう作るか | 変更 1 件につき設計書 1 本（`NNNN-<slug>.md`）。索引と [テンプレート](design/TEMPLATE.md) | 状態を「提案」→「承認」→「実装済み」と進める。実装後は記録として残し、決定の中身は変えない（読みやすさの修正は可） |
| [adr/](adr/README.md) | なぜその方針にしたか | 方針 1 件につき ADR（Architecture Decision Record。方針とその理由の記録）1 本（`ADR-NNNN-<slug>.md`）。索引と [テンプレート](adr/TEMPLATE.md) | 状態を「採用」→「廃止」と進める。決定の中身は変えず（読みやすさの修正は可）、覆すときは新しい ADR で置き換える |
| [roadmap/](roadmap/README.md) | いつ何をやり、いくらかかるか | フェーズと状態、着手前に決めること、AWS 化で決める構成、費用の見込み。節もこの順に並べる | フェーズの状態と費用を更新する |
| [review/](review/README.md) | この文書は決まりどおりに書けているか。設計どおりに実装されているか | 評価エージェント（Claude Code のエージェント `doc-review`、`design-review`。定義は `.claude/agents/`）の結果。文書 1 本につき 1 ファイル | 評価を回すたびに上書きする。古い結果は git の履歴で見る |

今はこの 5 種類だけです。手順書（起動、デプロイ、環境の削除）は、必要になった時点で足します。

## 設計書と ADR の使い分け

設計書と ADR はどちらも「決めたこと」を書くので、迷いやすい組み合わせです。主語が「変更」なら設計書、「方針」なら ADR と覚えます。

- 設計書は「変更」が主語です。影響するリポジトリ（[分け方](architecture/README.md#契約openapiとリポジトリの分割)）、契約（リポジトリの間のやり取りを決める OpenAPI の仕様。[用語](architecture/README.md#用語)）、認可、テスト、実装の段取り、未決事項まで書き、実装の入力にします。設計書の中の判断は、テンプレートの節「比較した代替案とトレードオフ」の表に書けば足ります
- ADR は「方針」が主語です。その設計書を読まない将来の変更にも効くルールと理由だけを短く書きます。例: [ADR-0003 生成コードは git で管理する](adr/ADR-0003-commit-generated-code.md)
- 迷ったら「この決定に、他の設計書も従わせたいか」で決めます。従わせたいなら、設計書に加えて ADR も書き、互いにリンクします
- 例: 契約とリポジトリ分割という変更は設計書 [0003](design/0003-contracts-and-repositories.md) に書き、そこから出た方針「型だけ生成する」「クライアントを成果物として配布する」は [ADR-0001](adr/ADR-0001-nuxt-generates-types-only.md) と [ADR-0002](adr/ADR-0002-distribute-clients-as-artifacts.md) に書きました。タスクの完了を冪等（同じ操作を何度行っても結果が変わらないこと）にする判断は設計書 [0004](design/0004-task-completion.md) の中だけに書き、ADR にはしていません

## 実装の段取りは設計書に書く

AI に実装を任せるときの段取り（PR の分割と順序、各段を終えてよい条件、手で行う操作）は、別の文書にせず設計書の「実装の段取り」の節に書きます。設計書の承認と一緒にレビューでき、設計書と二重にならないためです。AI が着手時に組み立てる細かい作業の一覧は、会話と PR 本文に残れば足ります。設計書が長くなりすぎたら、その節だけを別ファイルに出します。

## 書く順番

1 件の変更について、文書を書いてから実装に反映するまでの順番です。1 は、他の設計書にも従わせたい方針を決める変更のときだけ行います。

1. 他の設計書にも従わせたい方針を決める変更なら、ADR を書く（[adr/TEMPLATE.md](adr/TEMPLATE.md)）。索引 [adr/README.md](adr/README.md) に 1 行足す
2. 設計書を書く（[design/TEMPLATE.md](design/TEMPLATE.md)）。未決事項は決める人（作成者。AI が書くときは、指示した人）に質問し、無くなったら状態を「承認」にする。索引 [design/README.md](design/README.md) に 1 行足す
3. 書いた文書を `doc-review` エージェントで評価し、指摘を直し、要修正が 0 件になる（合格）まで繰り返す。手順はスキル（AI エージェント向けの手順書）[writing-docs](../.agents/skills/writing-docs/SKILL.md)、結果は [review/](review/README.md) に残す
4. 設計書の「実装の段取り」に沿って実装し、PR を出す。段取りと違う判断が要ったら、設計書を直して差分を PR に書く
5. マージ後、設計書に「実装 PR」を書き、状態を「実装済み」にする。`design-review` エージェントで設計と実装のずれを確かめ、結果を [review/](review/README.md) に残す。[architecture/](architecture/README.md) と [roadmap/](roadmap/README.md) を今の状態に合わせる

AI に任せるときのスキルとエージェントの一覧は [../AGENTS.md](../AGENTS.md) の表にあります。

## 書き方（人が読める文書にする決まり）

文書の読者は、その文書を書いたときの会話に居なかった人です。新しくチームに入った人が、他の文書を開かずに読み進められることを目標にします。次の表の決まりは番号で呼び、`doc-review` エージェントはこの番号で指摘します。

| 番号 | 決まり | 良い例と悪い例 |
|---|---|---|
| W-1 導入 | 先頭の表の次の段落で、「何の文書か」と「何を決める（説明する）か」を 2〜4 文で言う。設計書と ADR は「なぜ今か」も言う。索引、README、architecture、roadmap は「何の文書か」「何を載せているか」で足りる。「誰のために」は先頭の表の想定読者で足り、本文で繰り返さなくてよい。本文を表や箇条書きから始めない（先頭の表は除く） | 悪: 「業務環境では、画面と BFF の間も OpenAPI から型を生成していたが、クライアントは自前で書いていた。相性が悪いのかという疑問があった。」 良: 「画面（Nuxt）が BFF を呼ぶコードを、OpenAPI の契約からどこまで生成するかを決める。このリポジトリは作者が以前いた職場の構成を再現しており、その職場では型は生成し、クライアントは手で書いていた。」 |
| W-2 前提と用語 | 読者が役割を知らないと文が読めない語は、文書の中での初出に一言そえる。対象は、リポジトリ固有の前提（業務環境、集約リポジトリ、領域、契約、入口、前段）と概念語（JWT、BFF、SSR、IdP、冪等、publish）。製品名・ツール名（Keycloak、ALB、Karate、Flyway）は役割を一言そえる。コードの識別子（関数名、クレーム名）は、何をするか分からないと文が読めないときだけ。[architecture/ の「用語」](architecture/README.md#用語) にある語は、初出でその表へリンクすれば一言に代えてよい。初出が表のセルなら、表のリードで前出しする。他の文書の題名を引用した部分は対象外 | 良: 「業務環境（作者が以前いた職場。このリポジトリはその構成を学習用に再現している。[用語](architecture/README.md#用語)）」「Karate（API のテスト）」 |
| W-3 表のリード | 表、箇条書き、図、抜粋の前に、それが何を示しどう読むかを 1〜2 文置く。節を表だけで構成しない。表の後の文は、結論や注意があるときだけ書く。先頭の表、各項目が結論の文で始まる箇条書き、見出しが中身を言い切っている 1 行の表は除く | 良: 「次の表は、利用者の種別ごとに完了操作の可否を示す。社員はロールで、一般利用者は所有者かどうかで決まる。」 |
| W-4 理由 | 判断、採否、数値には理由を添える。理由が同じ文書の別の節にあるなら、その節名で参照すればよい。設定値は出所（どのファイルの値か）を書けば理由に代えてよい。表のセルは、意味が取れる名詞句なら体言止めでよいが、理由・判断・手順のセルは文にする | 悪: 「候補 \| typescript-fetch、openapi-fetch」 良: 「候補は 2 つ。typescript-fetch は HTTP の層まで生成し、openapi-fetch は型だけを生成する。」 |
| W-5 経緯を書かない | 会話で出た疑問や指示をそのまま書かない。「〜という疑問があった」「〜と分かった」「〜と言われた」「選んでもらう」「確認を取る」は、誰が、いつ、何を決めた（確かめた）かに直す | 悪: 「Nuxt と OpenAPI の相性が悪いのかという疑問があった。」 良: 「生成できるはずの部分をなぜ手で書いていたのかが分からず、Nuxt では生成したクライアントが使いにくいのかを確かめる必要があった。」 |
| W-6 文の形 | 1 段落は 4 文まで（短い段落は可）。1 文に 1 つのこと。主語を省かず「誰が、何を、どうする」の順に書く。手順の箇条書きと、方針を言い切る文（ADR の決定）は主語を省いてよい。矢印（→）や記号の羅列を文の代わりにしない。経路や順序は「A → B → C の順に流れる」のように文の中で使う | 悪: 「取得は匿名。」「状態: 提案 → 承認 → 実装済み。」 良: 「BFF は Reposilite から匿名でクライアントを取得する。」「状態は「提案」から始まり、未決事項が無くなったら「承認」に進む。」 |
| W-7 具体 | 値、ファイル名、URL、コマンド、画面の文言を具体的に書く。「適切に」「必要に応じて」で済ませない。「下記」「後述」「上の表」ではなく節名で指す。他の節や実装済みの設計書と食い違う記述（数、名前、一覧の抜け）を残さない | 良: 「`authz/src/main/resources/application.yml` の `task-admin` に `task:complete` を足す」 |
| W-8 見出しで追える | 見出しを読むだけで構成が分かる。節の中身が見出しと一致し、1 つの節に 2 つの話を入れない。同じ見出しを 2 回使わない | 悪: 「採用案」の節に代替案の比較が混ざる。「設計上のポイント」が 2 か所にある |
| W-9 言葉の統一 | 同じものは同じ言葉で呼ぶ。[architecture/ の「用語」](architecture/README.md#用語) に合わせる。一般名と具体名を両方使うときは、初出で「外部サービス（カレンダー API）」のように結び、以後は一般名で呼ぶ。同じ手順や事実を 2 つの文書に書かず、片方へリンクする | 悪: 同じ文書の中で「入口」「ゲートウェイ」「Nginx」が同じものを指す。「利用者」がアプリの利用者と文書の作成者の両方を指す |
| W-10 事実と仮定 | 業務環境の事実と学習用の仮定を分け、仮定を事実のように書かない。仮定は設計書の「制約と前提」か ADR の「状況」の表に 1 回書き、[architecture/ の「仮定」](architecture/README.md#仮定) の番号を付ける。本文で触れるたびに番号は要らない。この変更だけの仮定で architecture の表に無いものは「構成の仮定には載せない」と書く。業務環境と無関係の未決の選択は「仮定」と呼ばず「未決」か「前提」と書く | 良: 「認証 API の責務は不明なので、Keycloak のユーザー管理の代行と仮定する（仮定 12）」 |

この決まりは、評価の記録（[review/](review/README.md)）で同じ指摘が繰り返されたら見直します。決まりが曖昧で判定できない指摘は、`doc-review` が「決まり側の課題」として返します。

## 形式の決まり

次の表は、書き方の決まりとは別の、形式の決まりです。docs/ のすべての文書に当てはめ、`doc-review` はこの番号でも指摘します。

| 番号 | 決まり |
|---|---|
| F-1 日本語 | 日本語で書く。技術用語は英語のままで構わない |
| F-2 先頭の表と状態 | 各文書の先頭に、この文書と同じ表（発信日、作成者、機密区分、保守責任者、最終確認日、想定読者、読んだあとできること）を置く。設計書と ADR は、題名の次に `> **状態: 〜。**` の行を置く。最終確認日は、事実をコードや設定と照らして確かめ直したときに更新する。読みやすさだけの修正では変えない |
| F-3 テンプレートの節と行 | 設計書と ADR はテンプレートの節と表の行を揃える。該当しない節は本文に、該当しない行は削って同じ節の本文に、理由を 1 文書く。空欄のまま残さない。表の列名は、影響を受ける相手に合わせて変えてよい（例: 配布の失敗は「開発者への影響」）。テンプレートより前に書いた文書（実装済みの構成を後から記した as-built）は、無い節に「実装済みのため該当しない」のような 1 文で足りる |
| F-4 コードを書かない | 実装と二重になり古くなるので、文書にコードは書かない。契約の差分は OpenAPI の抜粋、設定の差分は設定ファイルの抜粋、記録の形は Markdown の抜粋で示してよい。図（mermaid）は書いてよい |
| F-5 リンク | 他の文書とは相対リンクでつなぐ。文書を名前で参照するときは必ずリンクにし、表示文言はパスではなく文書名や見出し名にする。設計書と ADR は互いにリンクする。少なくとも [architecture/](architecture/README.md) か索引へ 1 つはリンクする。ファイルを動かしたらリンクも直す |
| F-6 実装済みの文書 | 状態が「実装済み」の設計書は、未決事項を「なし」にし、将来に送ることは「課題・申し送り事項」に移す |
