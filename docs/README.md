## 種類と置き場所

次の表は、文書の種類ごとに、どの問いに答える文書をどのフォルダに置き、どう更新するかを示します。新しく文書を書くときは、まずどの行に当たるかを決めます。

| フォルダ | 答える問い | 置くもの | 更新のされ方 |
|---|---|---|---|
| [architecture/](architecture/README.md) | 今どうなっているか | 構成図、各サービスの役割、リクエストの流れ、業務環境の事実と学習用の仮定 | 常に最新にする。設計書が実装済みになったら、その内容をここに反映する |
| [design/](design/README.md) | この変更を、何を、どう作るか | 変更 1 件につき設計書 1 本（`NNNN-<slug>.md`）。索引と [テンプレート](design/TEMPLATE.md) | 提案 → 承認 → 実装済み。実装後は記録として残し、決定の中身は変えない（読みやすさの修正は可） |
| [adr/](adr/README.md) | なぜその方針にしたか | 方針 1 件につき 1 本（`ADR-NNNN-<slug>.md`）。索引と [テンプレート](adr/TEMPLATE.md) | 採用 → 廃止。決定の中身は変えず（読みやすさの修正は可）、覆すときは新しい ADR で置き換える |
| [roadmap/](roadmap/README.md) | いつ何をやり、いくらかかるか | フェーズ、状態、費用の見込み、着手前に決めること | フェーズの状態と費用を更新する |
| [review/](review/README.md) | この文書は決まりどおりに書けているか。設計どおりに実装されているか | 評価エージェント（`doc-review`、`design-review`）の結果。文書 1 本につき 1 ファイル | 評価を回すたびに上書きする。古い結果は git の履歴で見る |

今はこの 5 種類だけです。手順書（起動、デプロイ、壊し方）は、必要になった時点で足します。

## 設計書と ADR の使い分け

設計書と ADR はどちらも「決めたこと」を書くので、迷いやすい組み合わせです。主語が「変更」なら設計書、「方針」なら ADR と覚えます。

- 設計書は「変更」が主語です。影響するリポジトリ、契約、認可、テスト、実装の段取り、未決事項まで書き、実装の入力にします。設計書の中の判断は「比較した代替案」の表に書けば足ります
- ADR は「方針」が主語です。その設計書を読まない将来の変更にも効くルールと理由だけを短く書きます。例: [ADR-0003 生成コードは git で管理する](adr/ADR-0003-commit-generated-code.md)
- 迷ったら「この決定に、他の設計書も従わせたいか」で決めます。従わせたいなら、設計書に加えて ADR も書き、互いにリンクします
- 例: 契約とリポジトリ分割は設計書 [0003](design/0003-contracts-and-repositories.md)。そこから出た「型だけ生成する」「クライアントを成果物として配布する」は [ADR-0001](adr/ADR-0001-nuxt-generates-types-only.md) と [ADR-0002](adr/ADR-0002-distribute-clients-as-artifacts.md)。タスクの完了を冪等にする判断は設計書 [0004](design/0004-task-completion.md) の中だけで、ADR にはしない

## 実装の段取りは設計書に書く

AI に実装を任せるときの段取り（PR の分割と順序、各段を終えてよい条件、手で行う操作）は、別の文書にせず設計書の「実装の段取り」の節に書きます。設計書の承認と一緒にレビューでき、設計書と二重にならないためです。AI が着手時に組み立てる細かい作業の一覧は、会話と PR 本文に残れば足ります。設計書が長くなりすぎたら、その節だけを別ファイルに出します。

## 書く順番

1. 他の設計書にも従わせたい方針を決める変更なら、ADR を書く（[adr/TEMPLATE.md](adr/TEMPLATE.md)）。索引 [adr/README.md](adr/README.md) に 1 行足す
2. 設計書を書く（[design/TEMPLATE.md](design/TEMPLATE.md)）。未決事項はユーザーに質問し、無くなったら「承認」にする。索引 [design/README.md](design/README.md) に 1 行足す
3. 書いた文書を `doc-review` エージェントで評価し、指摘を直して合格させる。手順はスキル [writing-docs](../.agents/skills/writing-docs/SKILL.md)、結果は [review/](review/README.md) に残す
4. 設計書の「実装の段取り」に沿って実装し、PR を出す。段取りと違う判断が要ったら、設計書を直して差分を PR に書く
5. マージ後、設計書に「実装 PR」を書き、状態を「実装済み」にする。`design-review` エージェントで設計と実装のずれを確かめ、結果を [review/](review/README.md) に残す。[architecture/](architecture/README.md) と [roadmap/](roadmap/README.md) を今の状態に合わせる

AI に任せるときのスキルは [../AGENTS.md](../AGENTS.md) の表にあります。

## 書き方（人が読める文書にする決まり）

読者は、この文書を書いたときの会話に居なかった人です。新しくチームに入った人が、他の文書を開かずに読み進められることを目標にします。次の表の決まりは番号で呼び、`doc-review` エージェントはこの番号で指摘します。

| 番号 | 決まり | 良い例と悪い例 |
|---|---|---|
| W-1 導入 | 最初の段落で「何の文書か」「誰のために何を決める（説明する）か」「なぜ今か」を 2〜4 文で言う。表や箇条書きから始めない | 悪: 「業務環境では、画面と BFF の間も OpenAPI から型を生成していたが、クライアントは自前で書いていた。相性が悪いのかという疑問があった。」 良: 「画面（Nuxt）が BFF を呼ぶコードを、OpenAPI の契約からどこまで生成するかを決める。このリポジトリは作者が以前いた職場の構成を再現しており、その職場では型は生成し、クライアントは手で書いていた。」 |
| W-2 前提と用語 | このリポジトリ固有の前提（業務環境、集約リポジトリ、領域、契約、前段）と専門用語（JWT、BFF、SSR、冪等）は、初出で一言そえる。前提は [architecture/](architecture/README.md) にリンクする | 良: 「業務環境（作者が以前いた職場。このリポジトリはその構成を学習用に再現している。[構成の仮定](architecture/README.md#仮定)）」 |
| W-3 表のリード | 表と箇条書きの前に、それが何を示しどう読むかを 1〜2 文書く。表だけで節を終えない。表の後に結論や注意があれば 1 文足す | 良: 「次の表は、利用者の種別ごとに完了操作の可否を示す。社員はロールで、一般利用者は所有者かどうかで決まる。」 |
| W-4 理由 | 判断、採否、数値には理由を添える。表のセルも、理由が要る項目は体言止めにせず文で書く | 悪: 「候補 \| typescript-fetch、openapi-fetch」 良: 「候補は 2 つ。typescript-fetch は HTTP の層まで生成し、openapi-fetch は型だけを生成する。」 |
| W-5 経緯を書かない | 会話で出た疑問や指示をそのまま書かない。「〜という疑問があった」「〜と言われた」は、誰が、なぜ、何を確かめる必要があったかに直す | 悪: 「Nuxt と OpenAPI の相性が悪いのかという疑問があった。」 良: 「生成できるはずの部分をなぜ手で書いていたのかが分からず、Nuxt では生成したクライアントが使いにくいのかを確かめる必要があった。」 |
| W-6 文の形 | 1 段落は 3〜4 文。1 文に 1 つのこと。主語を省かず「誰が、何を、どうする」の順に書く | 悪: 「取得は匿名。」 良: 「BFF は Reposilite から匿名でクライアントを取得する。」 |
| W-7 具体 | 値、ファイル名、URL、コマンド、画面の文言を具体的に書く。「適切に」「必要に応じて」で済ませない | 良: 「`authz/src/main/resources/application.yml` の `task-admin` に `task:complete` を足す」 |
| W-8 見出しで追える | 見出しを読むだけで構成が分かる。節の中身が見出しと一致し、1 つの節に 2 つの話を入れない | 悪: 「採用案」の節に代替案の比較が混ざる |
| W-9 言葉の統一 | 同じものは同じ言葉で呼ぶ。[architecture/](architecture/README.md) の用語（入口、前段、IdP、契約、領域）に合わせる | 悪: 同じ文書の中で「入口」「ゲートウェイ」「Nginx」が同じものを指す |
| W-10 事実と仮定 | 業務環境の事実と学習用の仮定を分け、仮定を事実のように書かない。仮定には [architecture/ の「仮定」](architecture/README.md#仮定) の番号を付ける | 良: 「認証 API の責務は不明なので、Keycloak のユーザー管理の代行と仮定する（仮定 12）」 |

この決まりは、評価の記録で同じ指摘が繰り返されたら見直します。決まりが曖昧で判定できない指摘は、`doc-review` が「決まり側の課題」として返します。

## 共通の決まり

書き方の決まりとは別に、形式の決まりです。

- 日本語で書きます（技術用語は英語のままで構いません）
- 各文書の先頭に、この文書と同じ表（発信日、作成者、機密区分、保守責任者、最終確認日、想定読者、読んだあとできること）を置きます
- テンプレートの観点が該当しないときは、行ごと削って、該当しない理由を 1 行書きます。空欄のまま残しません
- 文書にコードは書きません。契約の差分は OpenAPI の抜粋で示します
- 他の文書とは相対リンクでつなぎます。ファイルを動かしたらリンクも直します
