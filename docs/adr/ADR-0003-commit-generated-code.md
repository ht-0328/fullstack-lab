## 状況

OpenAPI から生成したコードを git で管理するか（リポジトリにコミットするか）を決める。対象は、4 つの領域（`api` / `authz` / `auth` / `web` の各リポジトリ）が OpenAPI の仕様（領域同士をつなぐ契約。`openapi/*.yaml`。[用語](../architecture/README.md#用語)）から生成するコードで、コントローラーのインターフェース、DTO（リクエストとレスポンスの型）、クライアント、画面の型がある（[契約と生成物](../architecture/README.md#契約と生成物)）。この ADR より前は、「仕様が正」（手で書くのは `openapi/*.yaml` だけで、コードはそこから生成する）を徹底するため、生成コードを `build/` 配下に出してコミットしなかった。[設計書 0003](../design/0003-contracts-and-repositories.md) の「制約と前提」は、この ADR に従い、生成コードを git で管理すると書いている。

このリポジトリは、作成者が以前いた職場（業務環境）の構成を学習用に再現している（[構成の仮定](../architecture/README.md#仮定)）。業務環境では生成したコードを git で管理していたため、学習用の構成をそれに合わせるかを決める必要があった。

次の表は、決定の前提になる課題、制約、分かっている事実を分けて示す。この決定は業務環境の事実（生成コードを git で管理していた）だけを根拠にし、不確かなまま置いたことは無いので、仮定の行は置かない。

| 項目 | 内容 |
|---|---|
| 課題 | 生成コードをコミットすると「仕様だけ直して生成し忘れる」「生成コードを手で直す」事故が起こりうる |
| 制約 | 仕様が正であることは変えない。ホスト（コンテナを動かす側の環境。[用語](../architecture/README.md#用語)）に JDK（Kotlin のビルドに使う Java の開発キット）や Node（画面の型の生成に使う JavaScript の実行環境）を置かずに生成できる（これまでどおり Docker で完結する） |
| 事実 | 業務環境では生成コードを git で管理していた（[業務環境について聞いている事実](../architecture/README.md#業務環境について聞いている事実)） |

## 決定

OpenAPI から生成したコードをリポジトリにコミットする。生成は明示的な操作とし、ビルドは生成し直さない。仕様と生成物のずれは Docker の `check-generated` ステージ（Dockerfile の multi-stage build の 1 段）が検出する。

生成するコマンドは、集約リポジトリ（このリポジトリ fullstack-lab）では `./scripts/generate.sh`、各領域のリポジトリでは `./gradlew generate`（`web` の画面の型は `npm run generate:bff`）である。`check-generated` ステージは、`test` / `typecheck` のステージより先に生成し直し、コミットされた生成物と差分を取る。

次の表は、この決定が及ぶ範囲を示す。表の「成果物」は、仕様から生成したクライアントを Maven リポジトリ（Kotlin と Java のライブラリを置いて配布する場所）に登録（publish）して配布するライブラリを指す（[用語](../architecture/README.md#用語)）。

| 項目 | 内容 |
|---|---|
| 適用対象 | `api` / `authz` / `auth` の `src/generated`（インターフェースと DTO）と `client/src/generated`（クライアント）、`web/bff/src/generated`、`web/frontend/app/types/bff.d.ts` |
| 適用開始日 | 2026-10-28 |
| 対象外 | 生成器（インターフェースと DTO は OpenAPI Generator の `kotlin-spring`、クライアントは同じく `kotlin`、画面の型は `openapi-typescript`）の設定（`build.gradle.kts`、`package.json`）は従来どおり手で書く。画面の生成物に HTTP の層を含めない方針（[ADR-0001](ADR-0001-nuxt-generates-types-only.md)）と、クライアントを成果物として配布する方針（[ADR-0002](ADR-0002-distribute-clients-as-artifacts.md)）は変えない |
| 決定者 | ht-0328 |

## 理由

次の表は、決定の判断基準と、採用案（生成コードをコミットする）がどう評価されたかを示す。

| 判断基準 | 根拠 | 評価 |
|---|---|---|
| 業務環境との近さ | 業務環境では生成コードを git で管理していた | 同じ運用を学べる |
| レビューのしやすさ | 仕様の変更が、インターフェースや DTO の型の変化（必須の解除が `String?` になるなど）としてコードの差分に現れる | YAML の差分だけより影響が読める |
| 生成器の更新 | 生成器のバージョンを上げたときの出力の変化が PR の差分として見える | 生成器の出力が、PR の差分に出ないまま変わることが無い |
| clone 直後の体験 | IDE が生成タスクを走らせなくても参照を解決できる | 初回のビルドを待たずに読める |
| ずれの検出 | `check-generated` ステージが生成し直して `diff` を取る。生成し忘れと手直しは CI で落ちる | 「コミットしない」方式と同じ安全性を保てる |

## 結果と影響

次の表は、この決定で良くなることと悪くなることを、影響する対象とともに示す。

| 方向 | 内容 | 影響する対象 |
|---|---|---|
| 良くなること | 仕様の変更が、生成コードの差分としてレビューできる | PR のレビュアー |
| 良くなること | 生成器のバージョンとそのときの出力が同じコミットに残る | 生成器のバージョンを上げる開発者 |
| 良くなること | ビルドは生成器を実行せず、コミットされたコードをそのままコンパイルして、アプリの jar とクライアントのライブラリを作る | ビルドや CI を変える人（Docker の `package` ステージとクライアントの publish が生成器を実行しなくなる） |
| 悪くなること | 仕様を変えたら生成を実行してコミットする手順が増える | 仕様を変える開発者（手順はスキル（AI エージェント向けの手順書）[updating-openapi-contract](../../.agents/skills/updating-openapi-contract/SKILL.md)） |
| 悪くなること | 生成コードの差分が PR に混ざり、レビューの量が増える | PR のレビュアー |
| 悪くなること | `check-generated` ステージの分だけ、`test`（Kotlin）と `typecheck`（画面）のステージのビルド時間が延びる（`api` では、前のステージがキャッシュに乗っていても、このステージの Gradle（Kotlin のビルドツール）の起動と生成で 100〜110 秒。WSL の Docker で、`api` の `check-generated` ステージだけを作り直して測った値） | PR を出す開発者（CI の結果が出るまでの時間が延びる） |

`check-generated` がどの環境でも同じ判定になるのは、生成物が決定的（同じ仕様と同じ生成器のバージョンからは、どの環境でも同じ出力になること）だからである。生成器は既定で生成日時を生成物に入れない（`build.gradle.kts` と `package.json` に生成日時を入れる設定は無く、コミットされた生成物（`bff.d.ts` を含む）にも生成日時は含まれない）。生成タスク（`./gradlew generate`）は生成の前に前回の出力（`src/generated/kotlin`）を消すため、仕様から消えたエンドポイントや DTO が残ることもない。

## 検討したが採らなかった案

次の表は、検討した他の案と、採らなかった理由を示す。

| 案 | 利点 | 採らなかった理由 |
|---|---|---|
| ビルド時に生成し、コミットしない（従来） | 仕様と生成物が原理的にずれない。PR が小さい | 業務環境の運用と違う。生成器の更新による出力の変化が差分として見えない |
| コミットし、ビルドでも毎回生成し直す | 生成し忘れてもビルドは通る | ビルドのたびに生成し直すので、コミットされたコードと、実際にビルドに使われたコードが一致する保証が弱い。ビルドのたびに作業ツリーが書き換わる |
| 画面の型（`bff.d.ts`）だけコミットし、Kotlin はビルド時生成のまま | Kotlin の生成物（ファイル数が多い）の差分を避けられる | 業務環境と同じ運用を領域ごとに変えると分かりにくい。検出の仕組みも二重になる |
