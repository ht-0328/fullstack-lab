# ADR-0003 OpenAPI から生成したコードは git で管理する

| 項目 | 内容 |
|---|---|
| 発信日 | 2026-10-28 |
| 作成者 | ht-0328（Claude Code で作成） |
| 機密区分 | 公開可 |
| 保守責任者 | ht-0328 |
| 最終確認日 | 2026-10-28 |
| 想定読者（宛先） | 契約（`openapi/*.yaml`）を変える開発者、ビルドや CI を変える人 |
| この文書を読んだあと読者ができること | 生成コードをコミットしている理由と、仕様と生成物のずれをどこで防いでいるかを説明できる |

## 状況

各リポジトリは OpenAPI の仕様からコードを生成している。生成するのはコントローラーのインターフェース、DTO、クライアント、画面の型である。これまでは「仕様が正」を徹底するため、生成コードを `build/` 配下に出してコミットしなかった（[設計書 0003](../design/0003-contracts-and-repositories.md) の制約）。業務環境では生成したコードを git で管理していると分かった。学習用の構成をそれに合わせるかを決める必要があった。

| 項目 | 内容 |
|---|---|
| 課題 | 生成コードをコミットすると「仕様だけ直して生成し忘れる」「生成コードを手で直す」事故が起こりうる |
| 制約 | 仕様が正であることは変えない。ホストに JDK / Node を置かずに生成できる（これまでどおり Docker で完結する） |
| 事実 | 業務環境では生成コードを git で管理していた（2026-10-28 に確認） |

## 決定

OpenAPI から生成したコードをリポジトリにコミットする。生成は明示的な操作（`./scripts/generate.sh`、各リポジトリでは `./gradlew generate` / `npm run generate:bff`）とし、ビルドは生成し直さない。仕様と生成物のずれは Docker の `check-generated` ステージが検出する。このステージは `test` / `typecheck` の前段で生成し直し、コミットされた生成物と差分を取る。

| 項目 | 内容 |
|---|---|
| 適用対象 | `api` / `authz` / `auth` の `src/generated`（インターフェースと DTO）と `client/src/generated`（クライアント）、`web/bff/src/generated`、`web/frontend/app/types/bff.d.ts` |
| 適用開始日 | 2026-10-28 |
| 対象外 | 生成器の設定（`build.gradle.kts`、`package.json`）は従来どおり手で書く。生成物の HTTP 層を持たない方針（ADR-0001）と、クライアントを成果物として配布する方針（ADR-0002）は変えない |
| 決定者 | ht-0328 |

## 理由

| 判断基準 | 根拠 | 評価 |
|---|---|---|
| 業務環境との近さ | 業務では生成コードを git で管理していた | 同じ運用を学べる |
| レビューのしやすさ | 仕様の変更が、インターフェースや DTO の型の変化（必須の解除が `String?` になるなど）としてコードの差分に現れる | YAML の差分だけより影響が読める |
| 生成器の更新 | 生成器のバージョンを上げたときの出力の変化が PR の差分として見える | 黙って変わらない |
| clone 直後の体験 | IDE が生成タスクを走らせなくても参照を解決できる | 初回のビルドを待たずに読める |
| ずれの検出 | `check-generated` ステージが生成し直して `diff` を取る。生成し忘れと手直しは CI で落ちる | 「コミットしない」方式と同じ安全性を保てる |

## 結果と影響

| 方向 | 内容 | 影響する対象 |
|---|---|---|
| 良くなること | 契約の変更が、生成コードの差分としてレビューできる | PR のレビュー |
| 良くなること | 生成器のバージョンとそのときの出力が同じコミットに残る | 生成器の更新 |
| 良くなること | ビルドは生成器を実行しない。コミットされたコードがそのまま成果物になる | Docker の `package` ステージ、クライアントの publish |
| 悪くなること | 仕様を変えたら生成を実行してコミットする手順が増える | 契約を変える開発者（`updating-openapi-contract`） |
| 悪くなること | 生成コードの差分が PR に混ざり、レビューの量が増える | PR のレビュー |
| 悪くなること | `check-generated` ステージの分だけ `test` のビルド時間が延びる（Gradle の起動と生成で 10 秒程度） | CI |

生成物は決定的である（生成日時を埋め込まない設定にしている）。同じ仕様と同じ生成器のバージョンからは、どの環境でも同じ出力になる。生成の前に前回の出力を消すため、仕様から消えたエンドポイントや DTO が残ることもない。

## 検討したが採らなかった案

| 案 | 利点 | 採らなかった理由 |
|---|---|---|
| ビルド時に生成し、コミットしない（従来） | 仕様と生成物が原理的にずれない。PR が小さい | 業務環境の運用と違う。生成器の更新による出力の変化が差分として見えない |
| コミットし、ビルドでも毎回生成し直す | 生成し忘れてもビルドは通る | コミットされたコードが成果物と一致する保証が弱い。ビルドのたびに作業ツリーが書き換わる |
| 画面の型（`bff.d.ts`）だけコミットし、Kotlin はビルド時生成のまま | Kotlin の生成物（ファイル数が多い）の差分を避けられる | 業務環境と同じ運用を領域ごとに変えると分かりにくい。検出の仕組みも二重になる |
