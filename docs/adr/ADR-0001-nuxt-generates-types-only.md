# ADR-0001 画面（Nuxt）は OpenAPI から型だけを生成し、HTTP の層は生成しない

## 状況

画面（Nuxt）が BFF（画面専用のサーバー側 API。[用語](../architecture/README.md#用語)）を呼ぶコードを、OpenAPI の契約（画面と BFF の間は `web/openapi/bff.yaml`）からどこまで生成するかを決める。このリポジトリは、作成者が以前いた職場（業務環境）の構成を学習用に再現している（[構成の仮定](../architecture/README.md#仮定)）。その職場では、画面と BFF の間の契約も OpenAPI で定義し、TypeScript の型、DTO、コントローラーのインターフェースは生成していたが、BFF を呼ぶクライアント（リクエストを組み立てて送る部分）は手で書いていた。生成できるはずの部分をなぜ手で書いていたのかが分からず、Nuxt では生成したクライアントが使いにくいのかを確かめる必要があった。

次の表は、決定の前提になる課題、制約、分かっている事実、学習用に置いた仮定と、比べた候補を示す。課題に出る SSR は、サーバー側で HTML を作って返す描画で、Nuxt は初回の表示を Nuxt サーバーの中で行う。JWT は、ログインで発行される認証のトークンで、BFF が検証する（どちらも [用語](../architecture/README.md#用語)）。

| 項目 | 内容 |
|---|---|
| 課題 | SSR のときとブラウザのときで、BFF の呼び先とヘッダーの扱いが違う。SSR のときは Nuxt サーバーが `http://bff:8080/bff/*` を直接呼び、ブラウザのときは同一オリジンの `/bff/*` を呼ぶ。ブラウザからの呼び出しには入口（Nginx。AWS では ALB）が JWT（`x-amzn-oidc-accesstoken`）とリクエスト ID（`x-request-id`）を付けるが、SSR のときは入口を通らないので、Nuxt が元のリクエストから自分で BFF へ転送する必要がある |
| 制約 | 契約が画面と BFF の境界の唯一の定義であり、画面側の型は契約から生成する（[設計書 0003](../design/0003-contracts-and-repositories.md)） |
| 事実 | 業務環境では、画面側の型と DTO は OpenAPI から生成し、BFF を呼ぶクライアントは手で書いていた（[業務環境について聞いている事実](../architecture/README.md#業務環境について聞いている事実)） |
| 仮定 | 業務環境で画面側のクライアントを手で書いていた理由は分かっていない。このリポジトリでは、型だけを生成し `openapi-fetch` と手書きの composable で BFF を呼ぶ形を、業務環境の手書きのクライアントを型安全にしたものとみなす（[仮定 11](../architecture/README.md#仮定)） |
| 候補 | 候補は 2 つ。`openapi-generator` の `typescript-fetch` / `typescript-axios` は HTTP の層まで生成する。`openapi-typescript` は型だけを生成し、呼び出しは `openapi-fetch`（生成した型を使う薄い型付きクライアントのライブラリ）で行う |

## 決定

`openapi-typescript` で `paths` と `components` の型を生成し、`openapi-fetch` の薄い型付きクライアントを `useBff()` の中で組み立てる。HTTP の層は生成しない。`useBff()` は画面が BFF を呼ぶときに使う composable（`web/frontend/app/composables/useBff.ts`）で、SSR とブラウザの呼び先の切り替え、ヘッダーの転送、ブラウザで 401 になったときのログインへの誘導を受け持つ。

次の表は、この決定が及ぶ範囲を示す。

| 項目 | 内容 |
|---|---|
| 適用対象 | 画面から BFF への呼び出し（`web/frontend/app/composables/useBff.ts`） |
| 適用開始日 | 2026-10-28 |
| 対象外 | Kotlin 側のクライアント（BFF が API と認可 API を呼ぶ `api-client`、`authz-client`）。成果物（Maven のライブラリ）として配布する（[ADR-0002](ADR-0002-distribute-clients-as-artifacts.md)） |
| 決定者 | ht-0328 |

## 理由

次の表は、決定の判断基準と、採用案がどう評価されたかを示す。

| 判断基準 | 根拠 | 評価 |
|---|---|---|
| SSR との整合 | 生成クライアントが独自の HTTP の層（axios など）を持つと、Nuxt の `useAsyncData`（SSR で取得したデータをブラウザへ引き継ぐ、Nuxt のデータ取得の仕組み）と二重になり、呼び先の切り替えとヘッダーの転送を外側で包み直す必要がある | 型だけを生成する方式なら、`useBff()` の切り替えの処理がそのまま残る |
| 型安全 | `openapi-fetch` は、パス、パラメーター、レスポンス、エラーの型を `paths` から決める | 項目名や型の誤りがビルド時に分かる |
| 業務環境との近さ | 業務環境では、BFF を呼ぶクライアントを手で書いていた | 手で書いていたクライアントを型安全にした形に相当する（「状況」の表の「仮定」の行） |
| 学習の価値 | Nuxt で使いにくいのは OpenAPI そのものではなく、HTTP の層まで生成する方式であることを、動く形で示せる | 型だけを生成すれば Nuxt でも契約から生成できると、動くコードで説明できる |

## 結果と影響

次の表は、この決定で良くなることと悪くなることを示す。

| 方向 | 内容 | 影響する対象 |
|---|---|---|
| 良くなること | 契約（`web/openapi/bff.yaml`）を変えると、影響する箇所が画面側の型エラーとして現れる | 画面を変える開発者 |
| 良くなること | SSR とブラウザの切り替えと、ブラウザで 401 になったときのログインへの誘導を、`useBff()` の 1 か所に保てる | `useBff()` を保守する開発者 |
| 悪くなること | `openapi-typescript` が TypeScript 5 系を要求するため、6 系を使えない | `web/frontend` のビルドを保守する開発者 |
| 悪くなること | 呼び出しのたびに、`openapi-fetch` が返す `{ data, error }` を `unwrap()`（`useBff.ts` の関数。成功なら data を返し、失敗なら例外にする）で変換する | ページを書く開発者 |

## 検討したが採らなかった案

次の表は、検討した他の案と、採らなかった理由を示す。

| 案 | 利点 | 採らなかった理由 |
|---|---|---|
| `openapi-generator` の `typescript-fetch` / `typescript-axios` で HTTP の層まで生成する | 呼び出しコードを書かずに済む | 生成コードが独自の fetch / axios の設定を持ち、SSR のときの呼び先の切り替えとヘッダーの転送を外側で包み直すことになる。理由の詳細は「理由」の節の「SSR との整合」にある |
