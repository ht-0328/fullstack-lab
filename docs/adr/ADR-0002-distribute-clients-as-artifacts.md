# ADR-0002 領域間のクライアントは成果物（Maven）として配布し、ソースを共有しない

| 項目 | 内容 |
|---|---|
| 発信日 | 2026-10-28 |
| 作成者 | ht-0328（Claude Code で作成） |
| 機密区分 | 公開可 |
| 保守責任者 | ht-0328 |
| 最終確認日 | 2026-10-28 |
| 想定読者（宛先） | 契約を変える開発者、CI/CD を変える人 |
| この文書を読んだあと読者ができること | BFF が API のソースではなく成果物に依存している理由と、契約変更の順序を説明できる |

## 状況

画面 + BFF、API、認可 API をそれぞれ別リポジトリにした。BFF が API を呼ぶクライアントを、どこで生成し、どう受け渡すかを決める必要があった。業務環境では API クライアントを作っており、CodeArtifact を使っていた（用途の詳細は不明）。

| 項目 | 内容 |
|---|---|
| 課題 | 別リポジトリの契約から生成したコードを、リポジトリ間で安全に共有する |
| 制約 | 他の領域のソースを参照しない。契約の版を追跡できる |

## 決定

提供側（`api` / `authz`）が自分の契約からクライアントライブラリを生成し、Maven リポジトリへ publish する。利用側（`web/bff`）はバージョンを指定して依存する。同じバージョンは上書きしない。

| 項目 | 内容 |
|---|---|
| 適用対象 | `com.example.fullstacklab:api-client`、`authz-client` |
| 適用開始日 | 2026-10-28 |
| 配布先 | ローカル: Reposilite、CI: GitHub Packages、AWS: CodeArtifact（予定） |
| 決定者 | ht-0328 |

## 理由

| 判断基準 | 根拠 | 評価 |
|---|---|---|
| 境界の強さ | 利用側は成果物しか見ない。提供側の内部変更が漏れない | ソース参照より強い |
| 版の追跡 | `gradle.properties` の 1 行で「どの契約に追従しているか」が分かる | 追従の遅れが可視化される |
| 展開の独立 | 古い成果物が残るので、提供側と利用側を同時に展開しなくてよい | 契約の後方互換と組み合わせて安全 |
| 業務環境との近さ | CodeArtifact が担う役割をローカルと CI で再現できる | AWS 化で設定だけを変えればよい |

## 結果と影響

| 方向 | 内容 | 影響する対象 |
|---|---|---|
| 良くなること | 契約変更の手順が「版を上げる → publish → 追従」に固定される | 開発の流れ |
| 良くなること | 各リポジトリの CI が単独で通る | CI |
| 悪くなること | ローカルの起動が 2 段階になる（publish → up） | 開発者 |
| 悪くなること | 提供側のちょっとした変更でも、利用側で使うには版を上げて publish する必要がある | 提供側 |
| 悪くなること | BFF の Docker ビルドが Maven リポジトリへの到達を前提にする（host ネットワーク、資格情報） | ビルド環境 |
