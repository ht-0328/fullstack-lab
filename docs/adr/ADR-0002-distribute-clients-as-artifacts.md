# ADR-0002 領域間のクライアントは成果物（Maven）として配布し、ソースを共有しない

## 状況

BFF（画面専用のサーバー側 API）が API と認可 API を呼ぶクライアント（契約から生成した、リクエストを組み立てて送るコード）を、どのリポジトリで生成し、どう受け渡すかを決める。このリポジトリは、作成者が以前いた職場（業務環境）の構成を学習用に再現している（[用語](../architecture/README.md#用語)）。[設計書 0003](../design/0003-contracts-and-repositories.md) では、画面 + BFF、API、認可 API の 3 つの領域（独立したリポジトリで作る単位）をそれぞれ別のリポジトリにし、領域同士を OpenAPI の契約（領域同士の API の取り決め。各領域の `openapi/*.yaml`）だけでつなぐことにした。そのため、BFF が API と認可 API のソースを見ずにクライアントを手に入れる方法を、リポジトリを分けるのと同時に決める必要があった。

認証 API（`auth`）は、あとから[設計書 0005](../design/0005-auth-api-and-signup.md) で 4 つ目の領域として加わり、同じ方針で `auth-client` を配布している。この ADR に出てくる領域の数（3 つ）と提供側（API と認可 API）は、採用した 2026-10-28 時点の構成を指す。

次の表は、決定の前提になる課題、制約、分かっている事実と、学習用に置いた仮定を分けて示す。表の中の提供側は契約を定義して公開する側（API と認可 API）、利用側はそれを呼ぶ側（BFF）を指す。

| 項目 | 内容 |
|---|---|
| 課題 | 別のリポジトリにある契約から生成したコードを、リポジトリ間で安全に共有する |
| 制約 | 利用側は提供側のソースを参照しない。領域同士は契約だけでつなぐという [設計書 0003](../design/0003-contracts-and-repositories.md) の方針を守るためである。また、利用側がどのバージョンの契約に追従しているかを追跡できるようにする。追従の遅れを見つけるためである |
| 事実 | 業務環境では、API を呼ぶときに API クライアントを作っていた。また、CodeArtifact（AWS が提供する、Maven や npm のパッケージリポジトリ）を使っていたが、何に使っていたかは分かっていない |
| 仮定 | 業務環境では、API 側が生成したクライアントを Maven の成果物として publish（パッケージリポジトリに登録）し、BFF がバージョンを指定して依存していたと仮定する（[仮定 10](../architecture/README.md#仮定)）。BFF 側で生成していた可能性もある |

## 決定

提供側（API の `api` リポジトリと認可 API の `authz` リポジトリ）は、自分の契約からクライアントのライブラリを生成し、Maven リポジトリへ publish する。利用側（`web/bff`）は、バージョンを指定して依存する。同じバージョンは上書きしない。

上書きしないのは、同じバージョンを指定した利用側が、いつでも同じ成果物を取得できるようにするためである（CodeArtifact と同じ運用）。publish の手順（[scripts/publish-clients.sh](../../scripts/publish-clients.sh) と、提供側の各リポジトリの CI）は、同じバージョンが publish 済みなら何もしない。

次の表は、この決定が及ぶ範囲を示す。

| 項目 | 内容 |
|---|---|
| 適用対象 | `com.example.fullstacklab:api-client`、`authz-client`（2026-10-28 から）。`auth-client` も 2026-10-30 から同じ方針で配布している（[設計書 0005](../design/0005-auth-api-and-signup.md)） |
| 適用開始日 | 2026-10-28 |
| 対象外 | 画面（Nuxt）が BFF を呼ぶクライアント。型だけを生成し、成果物として配布しない（[ADR-0001](ADR-0001-nuxt-generates-types-only.md)） |
| 配布先 | ローカルは Reposilite（Compose の中で動かす Maven リポジトリ。`http://localhost:8081`）、CI は GitHub Packages（GitHub が提供するパッケージリポジトリ。`GITHUB_TOKEN` で取得する）、AWS は CodeArtifact。CodeArtifact への置き換えはフェーズ 6 の予定である（[ロードマップの「CodeArtifact が担当すること」](../roadmap/README.md#codeartifact-が担当すること)） |
| 決定者 | ht-0328 |

## 理由

次の表は、成果物として配布する方式を選んだ判断基準と、ソースを直接参照する方式と比べた評価を示す。

| 判断基準 | 根拠 | 評価 |
|---|---|---|
| 境界の強さ | 利用側は成果物しか見ないので、提供側の内部の変更が利用側に漏れない | ソースを直接参照する方式より、領域の境界が強い |
| バージョンの追跡 | `web/bff/gradle.properties` の 1 行（`apiClientVersion` など）で、どのバージョンの契約に追従しているかが分かる | 追従の遅れが見えるようになる |
| デプロイの独立 | 古い成果物が残るので、提供側と利用側を同時にデプロイしなくてよい | 契約の後方互換と組み合わせれば、片方ずつデプロイしても安全である |
| 業務環境との近さ | 「状況」の表の仮定のとおり、業務環境では CodeArtifact がクライアントの配布を担っていたと考える。その役割を、ローカルでは Reposilite、CI では GitHub Packages で再現できる | AWS 化のときは、コードを変えずに、Maven リポジトリの URL と資格情報の環境変数（`MAVEN_REPO_URL` など）を CodeArtifact 向けに変えればよい |

## 結果と影響

次の表は、この決定で良くなることと悪くなることを、影響する対象と合わせて示す。

| 方向 | 内容 | 影響する対象 |
|---|---|---|
| 良くなること | 契約を変える手順が、提供側がバージョンを上げて publish し、利用側がそのバージョンに追従する、という順に固定される | 契約を変える開発者（提供側と利用側の両方） |
| 良くなること | 各リポジトリの CI が、他のリポジトリを checkout せずに単独で通る | 各リポジトリの開発者と PR のレビュアー（他のリポジトリを待たずに CI の結果を確かめられる） |
| 悪くなること | ローカルの起動が 2 段階になる。`./scripts/publish-clients.sh` でクライアントを publish してから、`docker compose up -d --build --wait` で起動する | 開発者 |
| 悪くなること | 提供側のちょっとした変更でも、利用側で使うにはバージョンを上げて publish する必要がある | 提供側（`api`、`authz`、`auth`）の開発者 |
| 悪くなること | BFF の Docker ビルドは、ビルド中に Maven リポジトリへ到達できることを前提にする。ローカルでは `localhost:8081` の Reposilite に届くように、ビルドを host ネットワークで動かす（`compose.yaml` の `network: host`）。CI では GitHub Packages の資格情報（`MAVEN_REPO_USER`、`MAVEN_REPO_PASSWORD`）を、build secret（イメージに残らない形でビルドに渡す値）として渡す | CI を保守する人と、BFF をローカルでビルドする開発者 |

契約を変えるときの具体的な順序（提供側が仕様の `info.version` とクライアントのビルドの `version` を上げて publish し、利用側が `web/bff/gradle.properties` のバージョンを上げて追従する）は、[設計書 0003 の「契約を変えるときの順序」](../design/0003-contracts-and-repositories.md#契約を変えるときの順序) とスキル [updating-openapi-contract](../../.agents/skills/updating-openapi-contract/SKILL.md) にある。

## 検討したが採らなかった案

次の表は、検討した他の案と、採らなかった理由を示す。比較の全体は [設計書 0003 の「比較した代替案とトレードオフ」](../design/0003-contracts-and-repositories.md#比較した代替案とトレードオフ) にある。

| 案 | 利点 | 採らなかった理由 |
|---|---|---|
| BFF が API と認可 API のソースを直接参照する（同じリポジトリに置く、または git submodule で取り込む） | publish の仕組みもバージョンの指定も要らず、提供側の変更がすぐ利用側に届く | 提供側の内部の変更が利用側に漏れ、利用側がどのバージョンの契約に追従しているかも追えない。領域同士を契約だけでつなぐという[設計書 0003](../design/0003-contracts-and-repositories.md) の方針に反するため |
| BFF 側で API の仕様からクライアントを生成する | publish の仕組みが要らない | BFF が API の仕様ファイルを参照する経路が要り、どのバージョンの契約に追従するかの管理が BFF 任せになる。また、このリポジトリでは成果物を配布する流れを学ぶことを優先した |
