| 項目 | 内容 |
|---|---|
| 発信日 | 2026-11-01 |
| 作成者 | ht-0328（Claude Code で作成） |
| 機密区分 | 公開可 |
| 保守責任者 | ht-0328 |
| 最終確認日 | 2026-11-01 |
| 想定読者（宛先） | 文書を直す人、書き方の決まりと評価エージェントを育てる人 |
| この文書を読んだあと読者ができること | 文書ごとの評価の経過と残った指摘が分かり、どの文書でも繰り返される指摘から、直すべき決まりやテンプレートを見つけられる |

評価エージェントの結果を、文書 1 本につき 1 ファイルで残す場所です。人が PR で行うレビューはここには残しません。PR のコメントと修正コミットがその記録です。

残す理由は 2 つあります。1 つは、直さずに残した指摘の置き場にすることです。もう 1 つは、同じ指摘がどの文書でも出るなら、文書ではなく決まりかテンプレートが悪いので、それを見つけて直すためです。

## 置く結果

次の表は、ここに結果を置く 2 つのエージェントと、何を確かめるかを示します。

| エージェント | 確かめること | 対象 |
|---|---|---|
| `doc-review` | [書き方の決まり](../README.md#書き方人が読める文書にする決まり) どおりに書けているか | docs のすべての文書 |
| `design-review` | 設計書どおりに実装されているか | 設計書だけ。実装済みにするときに回す |

## ファイル名

対象のリポジトリのルートからのパスの `/` を `-` に変え、このフォルダに置きます。`docs/README.md` と `docs/review/README.md` を区別するために、`docs/` も含めます。

| 対象 | 記録 |
|---|---|
| `docs/design/0004-task-completion.md` | `docs/review/docs-design-0004-task-completion.md` |
| `docs/adr/ADR-0001-nuxt-generates-types-only.md` | `docs/review/docs-adr-ADR-0001-nuxt-generates-types-only.md` |
| `docs/architecture/README.md` | `docs/review/docs-architecture-README.md` |
| `docs/README.md` | `docs/review/docs-README.md` |

## 記録の形

次の形で書きます。評価を回すたびに「回ごとの結果」に 1 行足し、残した指摘と決まり側の課題を更新します。

```markdown
# 評価の記録: docs/design/0004-task-completion.md

| 項目 | 内容 |
|---|---|
| 対象 | [docs/design/0004-task-completion.md](../design/0004-task-completion.md) |
| 最終評価日 | YYYY-MM-DD |
| doc-review の結果 | 合格（2 回目で要修正 0 件） |
| design-review の結果 | 不一致なし（YYYY-MM-DD） |

## doc-review

次の表は、評価を回すたびに 1 行足します。「主な指摘」は決まりの番号で書きます。

| 回 | 要修正 | 直した | 残した | 主な指摘 |
|---|---|---|---|---|
| 1 | 7 | 7 | 0 | W-1、W-3 ×4、W-5 ×2 |
| 2 | 0 | 0 | 0 | 合格 |

### 残した指摘

| 決まり | 場所 | 指摘 | 残す理由 |
|---|---|---|---|

### 決まり側の課題

判定できなかった決まりや、他の文書でも出る指摘。docs/README.md やテンプレートを直す材料にする。

## design-review

| 項目（設計書の節） | 期待 | 実装の状態 | 判定 | 根拠 |
|---|---|---|---|---|
```

## 止める条件と回数の実績
